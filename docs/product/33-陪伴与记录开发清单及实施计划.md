## 1. 开发目标与范围

第一期目标：**把现有建档、照片库、时间线和作品能力串成直接可达、可靠留存的记录路径**，补齐照片日期/短句/标签和保存反馈。建档、上传、照片预览、删除、陪伴天数、去年今日、成长对比、作品付费均已有实现，不从零重建。

特别更正：现在已经可以在制作页保存宠物档案后退出，不生成作品。新增工作是让用户不必先选玩法，就能在档案页或照片库入口完成同一建档操作，不是新增建档服务。

| 工作范围 | 交付内容 | 完成的含义 |
| --- | --- | --- |
| 记录闭环 | 建档入口前移、图库直接上传、照片保留策略、可靠重试、日期/短句/标签、首页入口、完整回看、单张保存、私密与删除补强、接已有作品 | 第 8 章 A01–A18 全部通过，具备小范围体验条件 |

一期不引入宠物视觉识别、聊天陪伴、公开社区、每日打卡、自动生成收费作品或新会员套餐。不迁移技术栈，不接入 CloudBase。继续使用现有小程序 + Next.js API + PGlite/PostgreSQL + 对象存储。

本期不包含收藏、周期回顾、里程碑卡、生活节点扩展、亲友共建、批量导出或实体交付改造。本文不保留这些方向的开发任务、接口或排期。

**最先处理的阻塞：现有维护任务会清理超过一天且没有生成任务/作品引用的照片。** 记录产品不能沿用这个临时素材规则；必须先修订保留策略，再开放直接存图入口。

方案定稿时不实施模板上架、生成链路或页面接入。后续已按本文实施记录功能并同步功能清单及索引，当前状态见第 12 章；路线图、32 号文和下方素材决策保持原样。

## 1.1 AI 创意工坊第一批 12 个主题素材

### 需求结论

第一批共 12 个官方主题候选图，目标是把官网已验证的视觉质量沉淀为 AI 创意工坊的主题模板资产：

1. 先保留已在官网使用、表现较好的「飞行冒险」「潮流造型」「四季成长」3 个主题。
2. 另外新增 9 个主题，必须与前 3 个在叙事、道具和色彩构图上拉开差异。
3. 每个主题都要具备清晰的第一眼识别点、强趣味性和明确的尝试冲动；不能只做换色或换背景。
4. 宠物始终是画面主角，主题道具服务于玩法表达；不得出现可读文字、品牌 Logo、UI 截图或人宠混合身体。
5. 成品作为 AI 创意工坊的官方候选样片和后续模板参考，当前不代表已上架、冻结、seed 或进入生产。

### 统一风格规范

| 维度 | 规范 |
| --- | --- |
| 视觉定位 | 明亮、高级、商业化的宠物主题样片；实体布景与轻微 3D 质感结合，避免廉价贴图感 |
| 情绪 | 可爱、顽皮、轻松、想立即拿自家宠物尝试；避免阴暗、悲伤、医疗恐惧或过度复杂 |
| 色彩 | 珊瑚、奶油黄、天空蓝、淡紫、薄荷绿为主，允许单主题使用一处高对比色 |
| 构图 | 单只宠物为主要视觉焦点，主体完整、脸部清晰，重要内容位于画面中部安全区 |
| 输出 | 统一 4:3（1600×1200）候选图，后续模板可按实际玩法另做 3:4、9:16 或横版派生 |
| 禁止项 | 可读文字、字母、数字、水印、Logo、UI 截图、真实人物、重复宠物、明显解剖错误 |
| 适配要求 | 后续接入时必须验证猫/狗、长短毛、浅深毛色、正脸/轻侧脸等输入，不得只验证样片同品种 |

1. 先以「官网同款」候选专区进行内部预览，不直接把 12 个主题全部标记为 live。
2. 每个主题至少用 4 类输入验证：猫/狗各一类、浅/深毛色各一类、正脸/轻侧脸各一类；记录主体保真、构图完整和失败原因。
3. 样片与真实生成结果必须能对应：不得只展示精修样片而隐藏生成不稳定、主体被裁切或道具遮脸的情况。
4. 01–03 优先接入 AI 创意工坊；04、06、08、11 可作为互动/冒险场景扩展；07 可作为短片主题；03、09、12 可与成长记录、图文作品和纪念内容联动。
5. 「如果我是人」继续使用独立的人化链路，不把 12 个普通主题混入人化模板；健康助手、会员与实体也不作为普通 AI 工坊主题。
6. 后续实现应以「同一张宠物照片生成同主题的一组作品」为优先方向，例如海报、头像、壁纸或卡片保持同一视觉设定；具体张数、重试、计费和模板状态必须复用现有产品规则。
7. 通过真实输入回归、版权/素材审核和产品负责人确认后，才能冻结模板并进入现有图片模板注册、审核和发布流程；本次素材不构成发布授权。

## 3. 开发口径：消除上游歧义

下表是本文任务的具体选择，不回写 32 号文，也不覆盖支付合规、纪念克制等全局约束。

| 编号 | 问题 | 本次确定的实现口径 |
| --- | --- | --- |
| D01 | 自动识别宠物 | 用户确认所属宠物；优先入口 `petId`，其次默认宠物。无视觉识别；传入无权/已删除的 `petId` 时提示重新选择，不静默换成另一只 |
| D02 | 什么时候开始上传 | 选图后展示宠物、张数与保存说明，用户点「收好照片」才上传；取消选图不产生记录 |
| D03 | 一条记录是什么 | 一张已保存照片是一条记录；批次仅用于上传管理，不新建与照片重复的日记实体。每张可有自己的日期、短句和标签 |
| D04 | 最小输入 | 建档只必填名字、种类；照片可单张保存；文字、标签、生日/到家日都可跳过。生命阶段沿用 `active/senior/memorial`，不新增幼年枚举 |
| D05 | 第一批支持多少照片 | 每批 1–9 张，可继续追加下一批；串行上传。该数字是单批交互限制，不是账号总照片上限，也不承诺无限存储 |
| D06 | 免费与收费 | 基础记录、回看、元数据编辑、单张下载免费。PL-23 保持免费带水印；新陪伴卡一期不售卖；收费继续来自已有画册、短片等实际交付 |
| D07 | 即时回报 | 本期使用保存回执与已有时间线，不新增陪伴卡/里程碑卡生成器或收费项 |
| D08 | 自动续传 | 一期实现同一记录会话内的逐张重试与结果核对，不声称字节级断点续传或退出微信后后台上传。临时文件失效时仅失败项重选，成功项保留 |
| D09 | 重复照片 | 请求重试必须去重；用户重新选同一张则只给可能重复提示，可自行保留或删除。先做同一用户、同一宠物的上传字节哈希比较，不做人脸/相似图识别 |
| D10 | 顺序 | 时间线按记录日期；同日按稳定的创建时间、ID 排序。保留已有图库 `position` 及 Web 排序，不新增拖拽组件或改写用户已有顺序 |
| D11 | 首页与导航 | 三个 tab 为「陪伴 / 作品 / 我的」，路由与图标保持现有结构；主页依次展示宠物、记录主按钮、最近收好、实际命中的回忆、作品入口 |
| D12 | 纪念阶段 | 主动作改「收好照片」；不发今天打卡、生日召回或里程碑庆祝；过去式天数固定，无可靠截止日不给递增数字 |
| D13 | 文案是否能先上 | 保存、下载、私密、清理说明必须和能力一起交付；「原图备份」「永久保存」「删除后所有副本立即消失」不进入本期文案 |
| D14 | AI 与真实记录 | AI 成品保留在作品库，不能自动加入真实照片时间线；不从照片推断故事、疾病、心情、生命阶段，不添加模型调用 |

## 4. 一期页面与操作规则

### 4.1 独立记录路径

```text
陪伴首页 / 宠物档案 / 照片库 / 时间线
  → 现有照片库的记录模式（带 petId；无宠物时进入档案页建档）
  → 确认宠物并选图
  → 收好照片（逐张进度）
  → 已收好 X 张、失败 Y 张 / 重试失败项
  → 可选：给单张补日期、短句和标签
  → 查看这次记录 / 继续收好照片 / 返回陪伴首页
```

复用 `apps/miniprogram/pages/photos/photos?petId=...&mode=record`，在现有图库内展开选图/上传面板；普通进入图库不自动打开系统相册。照片详情与编辑复用抽屉组件。本期不新增记录页或详情页，不增加页面注册，只调整现有 tab 文案；继续使用 `themedPage`、现有组件和四套主题 token。

复用 `pages/pets` 的档案编辑抽屉，补 `mode=create`：新建 POST 既有 `/api/pets`，编辑保持 PATCH。图库无档案时导航至此，使用页面事件通道返回新宠物 ID 后返回图库；直接从「我的」进入新建则留在档案页。字段与 `create.savePet()`、`petInputSchema` 保持一致，不复制第三份表单、不改变原制作页的分步建档能力。

建档成功立即使用返回 ID，后续上传失败不重复建档。同名宠物允许存在，不按名字自动合并。按钮防连点；网络结果不明时先拉取档案让用户确认，不自动重试 POST。只建档后退出也必须成功，仍无生成任务/订单。

`petId` 在选图前确认，一批上传开始后锁定。切宠物前提示放弃尚未上传的选择，不能把已保存照片改挂到新宠物。所有结果、错误和成功提示带宠物名；切换宠物后过时的异步响应不能覆盖当前页面。

### 4.2 保存状态与失败处理

每张状态：`待上传 → 上传中 → 已保存 / 待核对 / 失败`；「已保存」必须有服务端返回或查询确认的照片 ID。

- 先处理格式/大小，再上传；沿用压缩策略并复查实际字节。压缩失败且原文件超限时明确提示，不能直接反复提交一个必失败文件。
- HTTP 进度 100% 仅代表发送完成，不显示「已收好」；需要确认对象已写入、数据库已落库。
- 超时/断网进入待核对，按稳定请求 ID 查询结果；查不到才以同一 ID 重试。网络/5xx 最多自动重试两次，指数退避；429 遵守等待提示，401 去登录，413/415/422 不自动重试。
- 部分成功时保留成功 ID，重试仅含失败/待核对项。不能重跑整个批次，也不因可选文字保存失败而回滚照片。
- 离页有未完成任务时说明结果，结束前台上传；重新进入优先核对已发出的请求。已发请求不能因用户离页就被当成未保存。
- 会话草稿按账号与宠物隔离；退出登录清理草稿。不要把故事正文、照片字节或凭据写入埋点；本地临时文件失效明确要求重选该张。
- 同请求 ID 重放且照片已删除，返回已删除状态，不能重新上传复活。

保存成功显示「已收进 {宠物名} 的时间线」「这次收好 {X} 张」「照片库共 {N} 张」。总数取服务端有效照片计数，不用前端数组长度；避免把重试成功说成「第 N 张新照片」。

### 4.3 日期、短句与标签

**日期字段分工：**

1. `created_at` 保留首次上传成功时间，不可由用户修改。
2. `shot_at` 保留收到文件时解析出的拍摄时间；缺失仍为空，不把手工日期伪装成 EXIF。
3. 新增 `memory_date`（可空 DATE），只存用户明确确认的记录日期。有效日期优先级：手工记录日期 → EXIF 对应日 → 上传对应日。
4. 有效日期来源返回 `manual/exif/upload`；页面分别写「你设置的日期 / 照片里的拍摄时间 / 按上传时间记录」。清除手工日期恢复原来源。

手工日期必须是有效完整年月日、不能晚于产品当天；可以早于建档或到家日。用户不知道日期时允许不填，不让用户为消除提示编造日期；一期不新增「大约某年」的模糊日期类型。

沿用 `domain/companion.ts` 与小程序 `services/companion.js` 的现有日期口径：纯日期按日历日处理，ISO 时刻按既有本地日转换；EXIF 继续走 `media/exif.ts`。本期不另推全仓固定时区策略、不重新解析历史照片。手工 `memory_date` 原样按 `YYYY-MM-DD` 存取，不经 `new Date('YYYY-MM-DD')` 转 UTC；有效记录日由服务端统一返回，页面直接显示，避免新增字段因手机时区转换偏一天。既有算法保留回归样本，不声称已经解决全仓跨时区行为。

时间线从服务端拿到有效日期和天数。现有 `dayIndexOf` 对早于起算日返回 1；本期仅在记录展示中隐藏这种不适用的天数，不修改全局算法影响旧作品。纪念阶段补收旧照不改变天数截止日，也不生成新的陪伴里程碑。

一句话最多 120 字符，纯文本，空字符串表示清空。六个固定标签为「今天的样子 / 第一次 / 散步 / 生日 / 学会了 / 只是想留着」，每张最多选三个；只存稳定标签代码，不从标签生成诊断或行为结论。用户主动点「应用到本次成功的 X 张」才可批量写同一句话/标签，不默认把一句话复制到不同日期。

修改采用版本检查；其他端已更新则提示重新加载，不能无声覆盖。标签与短句默认私密，不随旧作品分享自动公开；将来用于作品时需在制作预览中确认。

### 4.5 照片控制与可信说明

一期补照片库里的「下载保存的照片」操作，复用已有 `Photo.url` 对应的鉴权媒体读取及 `wx.downloadFile` → `wx.saveImageToPhotosAlbum` 方式，不新增一套下载后端。须检查 HTTP 状态、文件类型和相册授权结果；保存的是上传后实际文件，可能经过压缩，不承诺恢复手机原片，不能把私有媒体地址直接复制给访客。

照片删除前展示：从照片库移除且不能恢复；已导出的成品/他人已保存的副本不会被远程删除；需要关闭的作品分享应另行关闭。若有尚未完成的制作任务引用照片，返回冲突并列明「任务完成或取消后再删除」，不能让任务无提示地缺图。

删除成功后立即禁止新读取与新任务引用，图库、计数、时间线和最近记录同步移除。对象清理失败进入持久重试记录，不能被吞掉；用户界面可说「已从照片库移除」，物理删除完成前不说「已彻底清除」。头像、已有作品封面和成品必须使用各自受控的资源，不能为保住封面而让被删照片继续可访问。

原照片私有读取不得由 `works.public=true` 自动放开。公开分享需要的内容采用作品受控衍生文件或校验有效分享令牌的独立出口，并检查过期、撤销和删除状态。图像缓存不能让新的网络请求绕过撤销；已下载到他人设备的副本不作远程收回承诺。覆盖排版、AI、互动、视频和纪念分享的依赖回归后才上线此调整。

以上行为通过 A10/A11 后，可使用说明：「照片默认收在你的私人照片库。做成作品后，只有你主动开启的分享才会对外展示。你可以下载保存的照片，也可以从照片库移除。」

### 4.6 正常照片与临时对象的保留边界

`cleanupExpiredContent()` 现有 `orphanPhotos` 分支按「上传超一天且未被 generation_tasks/works 引用」清理照片。它会命中用户主动保存但未制作作品的照片；开一个新上传入口而不改这里，第二天记录可能消失。

本期明确：**正常 `photos` 记录不是临时素材，不因时间过去或没有作品引用而删除。** 规则同时适用于旧端上传、历史仍存在的照片和新记录入口；不要求逐张再标记「珍藏」才能保留。已经被旧清理删除的文件不能通过迁移恢复，也不能声称恢复成功。

复用现有维护任务，删除/收紧这条正常照片淘汰条件。只清理明确失败的上传对象和用户已删除照片的对象；锁定作品过期清理与限流记录清理保留原合同。上传失败孤立对象、照片删除重试接同一持久清理记录，执行前核对对象是否仍被有效记录使用，不按对象年龄猜测其可删。照片幂等墓碑不能被维护任务直接硬删，否则旧请求重放会再次创建照片。

`scripts/worker.ts` 自动轮次和 `/api/internal/maintenance` 手动入口必须验证同一规则；不新增第二套维护 Worker。A18 是所有直接存图入口放行前的必过项。

## 5. 数据、接口与兼容合同

本章保留方案定稿时的字段、模块和接口设计；当前实现与兼容边界以第 12 章及实施验收记录为准。

### 5.1 最小数据改动

| 位置 | 一期新增内容 | 不变量 |
| --- | --- | --- |
| `photos` | `memory_date`、`caption`、`tags`、`metadata_version`、`metadata_updated_at` | 旧记录读为空短句/空标签/无手工日期；原始日期和文件不覆盖 |
| `photos` | `upload_request_id`（旧端允许空）、`content_sha256` | 非空请求 ID 按 `(user_id, upload_request_id)` 唯一；墓碑保留请求键；哈希不跨用户查重 |
| `photos` 索引 | 用户/宠物/有效日期分页索引、用户/宠物/上传时间索引 | 游标含稳定 ID，不能只用日期翻页；计数排除已删除宠物和照片 |

照片读写继续使用 `platform-service.ts` 的已有函数；增量元数据/分页逻辑可以抽到 `src/server/photo-library-service.ts`，但旧入口与新入口必须调用同一实现，不复制 `savePhoto/listPhotos/deletePhoto` 三套逻辑。`src/domain/photo-memory.ts` 只组合现有日期工具和新增字段校验；下载继续走现有媒体路由，存储与事务沿用原适配器。

幂等写入必须处理并发竞争：对象落盘且照片事务成功后才能返回成功；唯一键竞争失败时读回同一条照片，清理本请求多写的孤立对象。相同请求 ID 携带不同宠物或不同文件哈希返回 409；不能返回一次旧请求的成功来掩盖新文件未保存。沿用上传路由现有对象补偿，再补补偿失败的持久重试；不能重新写一套并跳过原有大小/魔数/EXIF/限流检查。状态不明的同 ID 请求可安全查询/重试，不依赖内存锁。

元数据编辑以 ID、所有者、非删除状态和 `metadata_version` 一并匹配，再原子递增版本；批量编辑按整个批次校验，同事务全成功或返回冲突，由用户重新加载后重试。照片原文件已成功保存不受元数据事务失败影响。

新增迁移使用实施时的下一个空闲编号，不预占 `0030`。同步 Drizzle schema；运行时复用 `migrateDatabase` 自动发现和 `schema_migrations`。检查 `resetDatabaseForTest()` 对新增清理表和版本字段的隔离；验证旧库升级、新库初始化、迁移重复运行。

### 5.2 接口合同

沿用 `{ data }` / `{ error: { code, message } }`，所有写入遵循现有鉴权、请求来源校验和限频。边界使用 Zod，查询 UUID、游标、日期、标签、版本也必须校验。

| 接口 | 性质及请求 | 返回与关键行为 |
| --- | --- | --- |
| `POST /api/pets` | **原样复用**；名字、种类，其他可选 | 档案抽屉调用已有建档服务；不新增建档业务合同 |
| `POST /api/uploads` | 扩展 multipart：新增可选 `uploadRequestId`；新记录端必传 | 初次 201、同键重放 200，`data` 保留 Photo 形状并可带重复提示；旧端不传仍按旧合同处理 |
| `GET /api/uploads?requestId=...` | 新增；仅本人查询，ID 为 UUID | 已保存返回照片 ID/结果，已删除返回明确墓碑状态，未发现 404；不泄漏其他账号信息 |
| `GET /api/photos` | **扩展原路由**；新端显式传 `pageSize`、`petId`、`order=library/uploaded/recorded`、可选 `cursor` | 带 `pageSize` 时 `data={items,totalCount,nextCursor}`；不带时仍返回旧 Photo 数组。`library` 保留 position 顺序，首页取 uploaded 第一张 |

| `PATCH /api/pets/[id]/photo-metadata` | 新增；最多 9 个 `{photoId,version}` 加统一短句/标签 | 验证全部所属宠物与所有者；不把手工日期批量覆盖到不同照片 |

| `GET /api/pets/[id]/timeline` | 兼容扩展；新端传 `pageSize`，`cursor` 可选 | 保留 entries/anchor/milestones；分页模式增加 nextCursor/totalCount；旧服务调用的 limit 合同保留，不能因页面最高 100 条而截断内部 500 条调用 |
| `POST /api/annual-films` | 兼容扩展可选 `petId`，新宠物入口必传 | 明确指定宠物时不得自动挑另一只；不传保留账户级旧入口，返回实际主角供确认 |

`/api/photos` 现有 PATCH 是**整库排序**，不能改成元数据更新；旧 GET 未传 `pageSize` 时必须保持数组，新调用显式选择分页形状，不能让制作页/Web 图库突然收到对象。两个模式共享过滤和日期计算。`GET /api/photos/[id]` 和元数据 PATCH 当前确实缺失，属于新增；已有删除不能再列成从零开发。

游标绑定用户、宠物、排序条件和最后一条排序键；参数组合不匹配返回 422。删除、编辑日期或切宠物后废弃旧游标。读取、上传、下载、修改、删除都检查宠物未删除，不能只检查照片 `user_id`。

建议新增错误码：`UPLOAD_REQUEST_CONFLICT`、`PHOTO_VERSION_CONFLICT`、`PHOTO_IN_USE`、`PHOTO_DATE_INVALID`、`PHOTO_CURSOR_INVALID`。小程序请求封装补足 `statusCode` 和等待信息，上传与普通请求的错误码一致，供重试状态机使用。

| 旧照新传 | 易被误读为今天拍摄 | 「今天收好 · 记录日期 2023.06.01（你设置的日期）」 | T01/T06 |
| 下载入口 | 容易暗示原图 | 「下载保存的照片」；说明「文件可能经过上传压缩」 | T07 |
| 纪念记录 | 「记录今天」 | 「收好照片」；不自动添加情绪句或促销 | T05/T09 |
| 制作/支付 | 已有动态档位、价格及会员提示；新入口可能丢宠物上下文 | 保留现有报价区，正确传宠物；报价失败说明暂不可报价，不编造金额/权益 | T08 |

所有正式文案使用真实宠物名；加载时不闪现样板宠物/虚假天数。健康记录仍使用健康线措辞与独立权限，不混入情绪回顾制造结论。

## 10. 最小埋点与试用判定

复用现有 `events`，按事件对白名单元数据校验。ID 仅用于内部去重和归因，不上报故事、标签自由文本、照片地址、文件字节或设备相册信息。

| 事件 | 发出时机 | 核心字段/去重 |
| --- | --- | --- |
| `record_entry_opened` | 记录入口打开 | sessionId、entry、petId（允许无） |
| `upload_completed`（已有） | 保留现有事件名，扩展为首次成功落库才发出 | 增补 photoId、petId、uploadRequestId、entry；与记录事务/唯一键联动去重，不再另发 photo_saved 双计 |
| `photo_metadata_saved` | 元数据事务成功 | photoId、version、是否有短句/日期来源；无正文 |
| `memory_viewed` | 时间线或详情真正加载成功 | sessionId、petId、viewType；同会话同视图去重 |
| `record_deliverable_opened` | 用户主动从记录进入作品 | petId、产品 ID、entry；不算成交 |
| 既有成交事件 | 实际订单确认/权益核销 | 复用订单账本，不再由小程序发 `paid` 作为事实 |

一期观察四个指标：记录入口到首次照片成功率；首次记录后 7 天内在不同自然日再次保存的用户比例；7 天内回看比例；从记录入口到已有交付物的真实成交/权益使用率。旧图补传也是真实保存，但「照片年代」与「用户回访日」分开统计，不能把上传九张当作回访九次。

试用建议：先邀请愿意参与的 10–20 位宠主，观察至少 14 天并访谈首次存图后没有返回的人；这是定性试用规模建议，不是统计显著性声明。记录相同口径的基线/新版本人数和分母，不把微小样本的转化率上涨写成结论。

放行条件先看可靠性：不得存在维护误删、错宠物、越权读取、确认成功却找不到文件、重试重复落库、误收费。出现任一项立即关闭新入口并保留数据排查。留存差时先调整入口、记录成本和即时回报，不扩大本期范围或增加促销频次。

## 11. 发布、回退与断点续做

### 11.1 发布顺序

1. 完成 B0 基线和数据库备份，在隔离数据库演练迁移；检查旧客户端合同。
2. 先修正维护任务对正常照片的淘汰条件并验证 A18，再部署向后兼容的服务端增量；媒体隔离改动在测试环境跑全部分享类型回归。
3. 再发布既有图库的记录入口、档案抽屉与首页改动，完成小程序真机走查；出现问题通过兼容版本关闭新入口，保持已有照片读取/保存/删除可用，不为本期另建功能开关后台。
4. 通过一期可靠性验收后才开展小范围试用。真实对象存储、微信登录、支付通道、回调、iOS/Android 等按现有发布清单逐项验证。
5. 实际实施完成后，按 `21-小程序功能点清单.md` 对应页登记功能，`docs/README.md` 单点更新数量；不在本文另维护全仓页面/接口/测试总数。32 号文保持原文，本计划记录实际偏离。

本计划不授权正式发布、修改生产价格、冻结/上架待审图片模板或上传宠物人化 V2 效果；相关现有发布门槛继续有效。支付必须沿用 SKU 对应的合规通道，不能为方便试用改成模拟生产支付。

### 11.2 回退原则

- 页面问题：关闭新记录入口并回退到经过兼容测试的界面；保留照片回看/下载/删除。
- 数据/上传问题：暂停新记录写入，保留已成功数据，按请求 ID 查账；不能删除用户照片来清理统计。
- 服务端只能退到保留正常照片、兼容新增字段及私密读取约束的构建，不能恢复「无作品引用超过一天自动删除」或原照公开分支。
- 迁移只前进，不执行删列/删表式回滚；补丁修复保留元数据和幂等墓碑。
- 收费/作品问题：停受影响产品的新订单与生成任务，按既有退款/权益恢复流程处置，不影响基础记录。
