# 独立官网实施方案

把 `prototype/` 的静态原型改造成可部署的独立网站。**视觉与原型完全一致**，另加 SEO/GEO 基础设施与文章模块。

本文档只定方案，不含实现。三项已拍板：

| 决策 | 结论 |
| --- | --- |
| 部署形态 | **独立站、独立域名**，新增 `apps/website`，与 `apps/platform` 互不影响 |
| 文章内容源 | **Markdown 进 git**，Astro content collections 构建期渲染成静态页 |
| 品牌与域名 | **留占位** `{{BRAND_NAME}}` / `{{SITE_URL}}`，收口清单见第 10 章 |

---

## 1. 为什么独立站

`apps/platform` 有三处硬约束让官网不适合挂它路由下：

1. **`src/proxy.ts` 会拦截未登录访客**。生产模式下非公开前缀一律 302 到 `/login`，公开前缀只有 `/login` `/legal` `/share` `/interactive/share` `/memorial/share` `/annual-report/share`。官网挂进去必须改这个白名单，而这个文件管的是全站鉴权边界 —— 为官网放开一个前缀，等于在鉴权逻辑里增加一条与鉴权无关的规则。
2. **Next 16 的 SSR 首屏比静态文件慢**，且官网每次发布都要重建整个 platform 镜像、重启 web 容器。官网改一行文案不该让应用停一下。
3. **CSP 与 `next.config.ts` 共享**。官网若要接统计、地图之类第三方，改的是全站 CSP。

独立站换来的：静态文件可以走 CDN 或 Nginx 直发，不经 Node；发布是同步一个目录；出问题不影响应用。

### 域名规划

```
{{SITE_URL}}            → 官网（apps/website 静态产物）
www.{{SITE_URL}}        → 301 到主域（择一为规范域，另一个永久跳转）
app.{{SITE_URL}}        → 现有 apps/platform
```

**主域给官网而不是应用**，因为搜索流量落地页是官网。应用挪到 `app.` 子域需要同步改 `PUBLIC_APP_URL`（影响 `/api/plugins` 的样例图绝对路径拼接）与微信支付回调白名单 —— 这两处见第 9 章迁移清单。

## 2. 技术栈选型

### 选 Astro

| 项 | 值 | 理由 |
| --- | --- | --- |
| 框架 | **Astro 7**（当前 7.1.6） | 默认零 JS 输出、内容站是它的主场景；content collections 自带 schema 校验；`@astrojs/sitemap` 官方集成 |
| 内容 | Markdown + content collections | 文章进 git，改完提交即发布，无后台无数据库 |
| 样式 | **直接复用 `prototype/styles.css`** | 见下 |
| 输出 | 纯静态（`output: 'static'`） | 无 Node 运行时，Nginx 直发或上 CDN |
| Node | ≥ 22.12.0 | Astro 7 要求；仓库现有 Node 22.17 满足 |

**为什么不用 Next.js**：官网没有任何服务端逻辑（46 个链接里 43 个站内锚点、0 表单、0 网络请求）。用 Next 会引入 React 运行时与 RSC 那套机制去渲染一个静态页，且与 `apps/platform` 版本耦合。Astro 输出的 HTML 里默认没有框架 JS。

**为什么不用纯手写 + 脚本**：文章模块需要 Markdown 渲染、frontmatter schema 校验、列表分页、标签页、RSS、sitemap。这些自己写要几百行且容易出错，Astro 是现成的。

### 样式怎么复用

`prototype/styles.css` 是 1200 行原生 CSS，用 CSS 变量组织，**不依赖任何框架**。直接搬进 `apps/website/src/styles/site.css`，一行不改。

这一点很关键：**原型的视觉一致性由「同一份 CSS 文件」保证，不是靠人工比对**。改造过程中若发现必须改 CSS，说明有偏差，要停下来查。

Astro 组件里写 `<style is:global>` 引入这份文件，或在布局里 `import "../styles/site.css"`。

### main.js 怎么接

原型的 `main.js` 是 239 行 IIFE，`<script src="main.js">` 放在 `</body>` 前、直接 `querySelector`。搬进 Astro 有两个变化要处理：

1. **Astro 的 `<script>` 默认按 ESM 打包并带 `type="module"`**（隐含 defer），执行时机从「解析到就跑」变成「DOM 解析完」。原型的四块逻辑（hero 视频、入场时间线、滚动入场、菜单）都在 DOM 就绪后才需要动，**defer 反而更安全**，不需要改代码。
2. **hero 入场时间线依赖 `requestAnimationFrame` 双帧**（先让初始态生效再加 `.is-in`，否则 transition 不触发）。defer 下这个逻辑仍成立，但**必须实测** —— 时机变了要确认标题逐词滑入还在。

做法：`site.js` 原样搬入 `src/scripts/`，在 `BaseLayout.astro` 里 `<script src="../scripts/site.js">`（Astro 会处理打包）。**不要拆成多个组件各自带 script** —— 原型的四块逻辑共享 `reduced` 变量与一次性事件监听，拆开会重复注册。

### 素材：搬还是共用

`prototype/assets/` 的 30 个文件（bg.mp4 + 29 张图，7.9MB）**复制**进 `apps/website/public/assets/`，不做软链或构建期拷贝。

理由：原型要保持独立可运行（`docs/` 下双击就能看，这是它的价值），官网构建也不该依赖 `docs/` 目录。代价是 7.9MB 在仓库里存两份 —— 可以接受，且这批素材的真源在 `tools/imagegen/out/website/`，两处都是副本。

> 若日后素材更新，三处要同步：`tools/imagegen/out/website/`（真源）→ `docs/website/prototype/assets/`（原型）→ `apps/website/public/assets/`（官网）。这条值得写进发布脚本的检查项。

### 破坏性变更要留意

Astro 7 的 Rust 编译器**对无效 HTML 更严格**：未闭合标签会报错、非法嵌套不再自动纠正。原型的标签平衡已实测通过（我审计时验过），但迁移时若报错，先查 HTML 结构而不是绕过编译器。

另一条：`compressHTML` 默认值是 `'jsx'`，会按 JSX 规则剥掉行内元素之间的空白。原型里 hero 标题是逐词 `<span class="word">`，词间距靠 CSS `gap` 而非空格，不受影响；但迁移后要**实测标题渲染**，若出现粘连就在配置里设 `compressHTML: true`。

### 顶栏在无 hero 的页面要另给一套配色

这是实施时必然撞上的问题，先说清。原型顶栏是**为压在 hero 深色视频上设计的**：

```css
.topbar     { position: absolute; top: 0; }   /* 浮在 hero 内，不占文档流 */
.brand-name { color: #fff; text-shadow: 0 2px 6px rgba(0,0,0,.4); }
.menu-btn   { border: 1px solid rgba(255,255,255,.6); background: rgba(255,255,255,.1); color: #fff; }
```

文章页、标签页、法务页、404 都没有 hero。照搬会得到**浅底白字**，什么都看不见。

**做法**：`Topbar.astro` 接一个 `variant` 参数，`"hero"`（默认，首页用）与 `"solid"`（其余页面用）。新增 `.topbar-solid` 修饰类，只覆盖必要的几条：

| 属性 | hero 变体（现有） | solid 变体（新增） |
| --- | --- | --- |
| `position` | `absolute` | `sticky; top: 0`（滚动时保留导航） |
| 背景 | 无（透明） | `var(--surface)` + 下边框 `var(--border)` + `backdrop-filter` |
| 品牌名 | `#fff` + 文字阴影 | `var(--text-primary)`，无阴影 |
| 菜单按钮 | 白描边白字 | `var(--border-strong)` 描边 + `var(--text-primary)` |
| 桌面下拉面板 | `rgba(42,31,31,.72)` 深底白字 | 同样保持深底 —— 它是浮层，深底在浅色页上对比度更高 |
| 入场动画 | 有（`y:-40 → 0`，1.4s） | 无 —— 文章页不需要入场表演 |

**这不算「与原型不一致」**：原型只有首页，solid 变体是新页面类型必需的新增，首页的顶栏一个像素不动。第 13 章第 1 步的逐像素比对只针对首页。

对比度按新底色实算过：`--text-primary`（#3A2C2C）在 `--surface`（#FFFDFA）上 **13.12:1**，正文次色 `--text-secondary` 5.54:1、主色 `--primary` 5.20:1，都达标。

**`src/config/site.ts` 集中所有可变文案**（品牌名、导航项、玩法清单、玩法卡文案）。原型里这些散在 HTML 各处，品牌名出现 4 次、导航项在桌面下拉与移动面板各一份。集中后收口只改一个文件，且两个菜单不会写歪 —— 原型里它们是手写的两份，改一个忘一个不会报错。

## 4. 路由与页面

| 路由 | 内容 | 备注 |
| --- | --- | --- |
| `/` | 首页 11 区块 | 与原型完全一致 |
| `/blog/` | 文章列表，每页 12 篇 | 按 `publishedAt` 倒序 |
| `/blog/2/` `/blog/3/` … | 分页 | `paginate()` 生成 |
| `/blog/<slug>/` | 文章详情 | slug 由文件名或 frontmatter 指定 |
| `/blog/tag/<tag>/` | 标签页 | 标签从 frontmatter 汇总 |
| `/legal/terms/` | 用户协议 | 先放章节骨架 + 未定稿提示条，见第 11.1 章 |
| `/legal/privacy/` | 隐私政策 | 同上 |
| `/404.html` | 404 页 | 复用 BaseLayout，给回首页与文章列表的出口 |
| `/rss.xml` | RSS 2.0 | `@astrojs/rss`（是普通包，不是 integration，在 endpoint 文件里 import） |
| `/sitemap-index.xml` + `/sitemap-0.xml` | sitemap | `@astrojs/sitemap` 自动生成两个文件：index 指向编号文件 |
| `/robots.txt` | 爬虫规则 | 静态文件 |
| `/llms.txt` | 站点结构给 AI agent | 见第 7 章的定位说明 |

**URL 末尾统一带斜杠**（`trailingSlash: 'always'`）。静态托管下 `/blog/foo` 与 `/blog/foo/` 会被搜索引擎当两个 URL，统一一种再配 canonical。

> 实施时要**实测 sitemap 输出的 URL 是否也带斜杠**。`@astrojs/sitemap` 的文档没有提 `trailingSlash`，示例里的 URL 带斜杠但那是 Astro 默认行为的体现，不能证明该集成会读这个配置。若不一致，用 `serialize()` 统一。canonical 与 sitemap 逐字一致这条不能破。

**法务页在原型里是死链**：页脚的「用户协议」「隐私政策」都指向 `#home`。本方案把两页真正建出来，**正文先放章节骨架 + 未定稿提示条**（已定的处理方式，口径见第 11.1 章），正文定稿前不对真实用户开放。

## 5. 文章模块

### frontmatter schema

配置在 **`src/content.config.ts`**（Astro 7 的位置，不是旧版的 `src/content/config.ts`）。字段缺失或类型不对会在构建时报错而非静默出错：

```ts
// 三个导入路径都别记错：defineCollection 来自虚拟模块 astro:content，
// z 来自 astro/zod（Astro 6 起从 astro:content 挪走了），glob 来自 astro/loaders。
import { defineCollection } from "astro:content";
import { glob } from "astro/loaders";
import { z } from "astro/zod";

const posts = defineCollection({
  loader: glob({ base: "./src/content/posts", pattern: "**/*.md" }),
  schema: ({ image }) => z.object({
    title: z.string().max(60),           // 超 60 字在搜索结果里会被截断
    description: z.string().min(50).max(160), // meta description 的有效区间
    publishedAt: z.coerce.date(),
    updatedAt: z.coerce.date().optional(),
    cover: image().optional(),           // 交给 Astro 处理尺寸与格式
    coverAlt: z.string().optional(),
    tags: z.array(z.string()).default([]),
    author: z.string().default("{{BRAND_NAME}}"),
    draft: z.boolean().default(false),   // true 时不进构建，也不进 sitemap/RSS
  }),
});

export const collections = { posts };
```

两条会咬人的：

- **`getCollection()` 的返回顺序不确定**（官方说法：non-deterministic、依赖平台）。列表页、RSS、sitemap 都必须显式 `sort()` 按 `publishedAt` 排，否则换台机器构建就会得出不同顺序。
- **`image().refine()` 不支持**。要校验封面图尺寸得在别处做，schema 里只能声明 `image()`。
- 若 `tsconfig.json` 继承 Astro 的 base 模板，schema 需要 `strictNullChecks` 与 `allowJs`。

`title` 与 `description` 加长度上限是刻意的 —— 它们直接进 `<title>` 与 `meta description`，超长会被搜索结果截断。schema 挡住比上线后发现更省事。

`cover` 用 `image()` 而非 `z.string()`：Astro 会校验文件存在、并在构建时生成多档尺寸与 `width`/`height`（防 CLS，与原型同一个考虑）。

### 文章文件示例

```markdown
---
title: 宠物身份证怎么做才像真的
description: 一张正脸照就能生成宠物身份证。这篇讲清楚照片怎么选、字段怎么填，以及为什么陪伴天数要按日历日算。
publishedAt: 2026-08-15
tags: [玩法教程, 宠物身份证]
cover: ./images/id-card-guide.jpg
coverAlt: 桌面上平摊的宠物身份证成品
---

正文用 Markdown。h1 由 title 生成，正文从 h2 起。
```

### 文章正文样式必须新增（原型没有）

实测 `prototype/styles.css`：**完全没有正文排版样式** —— 没有 `h4`/`h5`/`blockquote`/`pre`/`code`/`table`/`ol`/`hr`/`strong`/`em`，也没有 `a:hover`。它只服务首页那 11 个区块。

更麻烦的是两条全局重置会直接破坏文章正文：

```css
ul { margin: 0; padding: 0; list-style: none; }   /* 文章里的列表会没有符号 */
a  { color: inherit; text-decoration: none; }     /* 正文链接会看不出是链接 */
```

**做法：新增 `src/styles/prose.css`，作用域限定在 `.prose` 容器内，不改 `site.css` 一个字。**

```css
/* 只在文章正文生效，把全局重置在这个作用域内还原回来 */
.prose ul { padding-left: 1.5em; list-style: disc; }
.prose ol { padding-left: 1.5em; list-style: decimal; }
.prose a  { color: var(--primary); text-decoration: underline; text-underline-offset: 0.2em; }
.prose h2 { /* 复用 --fw-semibold / --ls-tight 等既有 token，不新造取值 */ }
...
```

**取值一律引用 `site.css` 里已有的 CSS 变量**（字号、字重、行高、色彩、间距都有），不新造。这样文章页与首页是同一套视觉语言，且改主色只需改一处。

正文链接**要有下划线**：首页的链接都在按钮或卡片里、位置本身提示可点，正文里的行内链接没有这个语境，只靠颜色区分对色觉障碍用户不友好。

### 发布流程

改完提交即发布，无后台：

```
写 src/content/posts/<slug>.md  →  cd apps/website && pnpm build（schema 校验 + 生成静态页）
                                →  提交推送  →  部署脚本同步 dist/
```

`draft: true` 的文章不进构建产物，也不进 sitemap 与 RSS。

## 6. 小程序码：三个触点

原型只在第 9 区块的 CTA 面板里放了一处小程序码（虚线占位框）。它在页面底部，用户要滚到底才看得到 —— 而小程序码是**全站唯一的转化出口**。现补两个常驻触点：

| # | 位置 | 触发 | 说明 |
| --- | --- | --- | --- |
| 1 | 顶栏「菜单」按钮左侧 | 悬停/聚焦 | 首屏就能看到，与菜单按钮同高同圆角 |
| 2 | 页面右下角悬浮 | 悬停/聚焦 | 固定位置，滚到哪都在 |
| 3 | 第 9 区块 CTA 面板（原有） | 常显 | 不动，它是落地区的主 CTA |

三处**共用同一个 `QrPopover.astro` 组件**，二维码图片路径在 `src/config/site.ts` 定义一次。这样换真实小程序码只改一处，不会漏。

### 6.1 弹框设计

要求是「可爱一点」，但项目基调是**精致而非可爱**（根 `CLAUDE.md` 的 UI 重构拍板）。这两条不冲突 —— 拍板同时允许**黏土质感限 3 处**作为可爱感的出口。小程序码弹框是恰当的第 4 处：它是个小面积、高愉悦度的交互点，正是黏土适合的场景。

> **黏土用量要记一笔**：原型已用 1 处（纪念区图框）。加上这个弹框是 2 处，仍在 3 处限额内。若日后还要加，先回看拍板全文。

弹框结构（取值全部来自 `site.css` 已有变量，不新造）：

```
┌─────────────────────┐
│  🐾                 │  ← 爪印 SVG，右上角，opacity .12，纯装饰
│   ┌───────────┐     │
│   │           │     │
│   │  小程序码  │     │  ← 168px，圆角 --radius-card，内嵌阴影让它「陷进」黏土面
│   │           │     │
│   └───────────┘     │
│                     │
│   微信扫码开始创作    │  ← 14px，--text-primary
│   第一次创作不花钱    │  ← 12px，--text-tertiary
└──────────▼──────────┘  ← 小尾巴三角，指向触发按钮
```

四层黏土（与纪念区图框同一套，`--clay-highlight` + `--shadow-clay`）：

```css
.qr-pop {
  padding: 16px;
  border-radius: var(--radius-clay);          /* 28px，比卡片大一档 */
  background: var(--card);
  box-shadow: var(--clay-highlight) 0 5px 0 0 inset, var(--shadow-clay);
}
.qr-pop img {
  border-radius: var(--radius-card);
  box-shadow: inset 0 3px 9px rgba(58,44,44,.28);   /* 嵌进黏土表面 */
}
```

「可爱」由三处细节承担，都不引入新的设计语汇：

1. **入场带轻微过冲**：`{opacity:0, scale:.9, y:8}` → `1/1/0`，用 `--ease-spring`（已有变量，hero 标题逐词滑入用的就是它）。落点有一点弹性，像轻轻蹦出来
2. **爪印装饰**：右上角一枚爪印 SVG，`opacity: .12`，纯装饰（`aria-hidden`）。与页面其他图标同一个 `stroke-width: 1.6`
3. **小尾巴三角**：弹框指向触发按钮的小三角，用 `::after` + `border` 画，不用额外元素

**不做的**：不加彩色渐变、不加多色描边、不加弹跳循环动画。这些会越过「精致」的线。

### 6.2 悬停在触屏上无效 —— 交互要双轨

这是这个需求最容易做错的地方。规格 2.7 的自定义光标撞过同一堵墙：「小程序是主场景，官网来访大概率过半是微信内移动端，`cursor` 在触屏完全无效」—— 它最终的做法是**用 `matchMedia("(pointer: fine)")` 判断指针能力，不满足就整块不启用**（该功能已实现，见规格 9.1 章偏离 ⑯）。

**同一个理由适用于悬停**，但结论不同：光标在触屏上可以「不启用」，因为它是纯装饰；**小程序码不能** —— 它是唯一转化出口，触屏用户必须能打开。所以这里不是「判断后放弃」，而是**双轨**：有悬停能力走 hover，没有就走 click。

若只写 `:hover`，移动端用户点按钮会没有任何反应，而移动端恰恰是主要流量。

做法：

```js
// 用 matchMedia 判断「真的有悬停能力」，而不是判断视口宽度 ——
// 平板接键鼠、触屏笔记本都存在，按宽度判会判错。
const canHover = matchMedia("(hover: hover) and (pointer: fine)").matches;
```

| 环境 | 打开 | 关闭 |
| --- | --- | --- |
| 有悬停能力（桌面） | `mouseenter` / `focusin` | `mouseleave` / `focusout` / `Esc` |
| 无悬停能力（触屏） | `click` | 再次 `click` / 点弹框外 / `Esc` |

三个实现细节：

- **弹框必须是触发按钮的子元素**（或与按钮之间零间隙）。若中间有空隙，鼠标从按钮移到弹框上会先触发 `mouseleave`，弹框闪一下就关。
- **`focusin`/`focusout` 而非 `focus`/`blur`**：前者会冒泡，弹框内的元素得到焦点时不会误判成失焦。
- **触屏下 `click` 打开后要防止 `mouseleave` 立刻关掉**。某些浏览器会在 tap 后合成鼠标事件。用一个 `openedByClick` 标记挡掉。

键盘可达：触发按钮是 `<button>`（不是 `<div>`），带 `aria-expanded` 与 `aria-describedby` 指向弹框；Tab 能聚焦、Enter/Space 能开、Esc 能关且焦点还回按钮。这套与原型的菜单按钮同构，直接照搬那段逻辑。

`prefers-reduced-motion: reduce` 下弹框直接显示，不做入场动画 —— 与原型现有的 reduced-motion 分支一致。

### 6.3 顶栏按钮

放在「菜单」按钮**左侧**（菜单是原型里最右的元素，保持它在最右）。与菜单按钮同高（38px）、同圆角（`--radius-pill`）。

**两套配色跟着顶栏变体走**（见第 3 章的 `variant` 说明）：hero 变体用白描边白字，solid 变体用 `--border-strong` + `--text-primary`。

内容：爪印图标 + 「扫码」二字。只放图标辨识度不够 —— 用户不知道点了会出什么。

**移动端（<768px）隐藏这个按钮**：顶栏在 390px 下只放得下品牌名与菜单按钮，再加一个会挤。移动端靠右下角悬浮按钮，功能不缺。

### 6.4 右下角悬浮按钮

```css
.qr-fab {
  position: fixed;
  right: 20px;
  /* 底部留出 iOS 安全区，否则在 iPhone 上会被 Home 指示条压住 */
  bottom: calc(20px + env(safe-area-inset-bottom, 0px));
  z-index: 30;
}
```

**z-index 要排进现有层级**，原型已有三层：顶栏 20、移动全屏菜单 40、桌面下拉 50（在顶栏的 20 内）。悬浮按钮取 **30** —— 高于顶栏、低于移动菜单，这样菜单打开时它被盖住（该被盖住，全屏菜单是模态）。

**两条显示规则**，都是为了不碍事：

1. **hero 内不显示**。首屏已经有主 CTA「开始创作」，悬浮按钮在那里是重复且遮挡。用 `IntersectionObserver` 观察 hero，离屏后才淡入 —— 原型的 `main.js` 已经在用 IO 做视频离屏暂停，同一个模式。
2. **滚到第 9 区块（CTA 面板）时淡出**。那里已经有一个更大的小程序码，两个同时出现是冗余。同样用 IO 观察 `#contact`。

移动端位置要避开可能的系统手势区，`right: 16px` / `bottom: 16px + safe-area`。

## 7. SEO 与 GEO

先说清一件事：**GEO 没有独立的技术手段**。Google 官方 AI 优化指南明确说，AI Overviews 与 AI Mode 建立在核心 Search 索引之上（RAG grounding + query fan-out），因此「针对生成式 AI 优化」就是 SEO 本身；**不需要特殊的 schema.org 标记，也不需要为 AI 改写内容**。真正的门槛是页面被索引、可带摘要展示、内容可抓取。

下面按「确定有效 → 廉价保险」排列。

### 7.1 每页必备的元信息

`Seo.astro` 组件统一输出，各页传参：

```
<title>            ≤60 字，格式「页面标题 · {{BRAND_NAME}}」，首页单独写
<meta description> 50–160 字，每页不同，不复用
<link canonical>   绝对 URL，带 trailingSlash，与 sitemap 一致
og:type            首页 website，文章 article
og:title / og:description / og:image / og:url / og:site_name
og:image           1200×630，文章用封面图，其他页用统一的品牌图（待提供）
twitter:card       summary_large_image
<html lang="zh-CN">
```

**canonical 必须与 sitemap 里的 URL 逐字一致**（协议、www、末尾斜杠）。不一致时搜索引擎会认为存在重复内容。

### 7.2 结构化数据（JSON-LD）

Google 说生成式 AI 不需要特殊 schema，但**常规搜索的富结果需要**。按页面类型给：

| 页面 | 类型 | 关键字段 |
| --- | --- | --- |
| 全站（在 BaseLayout） | `Organization` | `name` `url` `logo` `sameAs`（社交账号，待提供） |
| 首页 | `WebSite` | `name` `url` `inLanguage: zh-CN` |
| 文章详情 | `Article` | `headline` `description` `datePublished` `dateModified` `author` `image` |
| 文章列表 | `Breadcrumb` | 首页 → 文章 |
| 文章详情 | `Breadcrumb` | 首页 → 文章 → 标题 |

**不要加 `Product` 或 `Offer`** —— 官网不直接售卖，价格在小程序内。虚标结构化数据是搜索作弊。

**`FAQPage` 视情况**：Google 已大幅收窄 FAQ 富结果的展示范围，别为了它硬造问答。若文章本身是 Q&A 形态再加。

### 7.3 sitemap 与 robots.txt

`@astrojs/sitemap`（3.7.3）自动生成，配置里要给 `site`（绝对域名）否则不输出。排除项：`draft` 文章、`/404`。

`robots.txt`：

```
User-agent: *
Allow: /
Sitemap: {{SITE_URL}}/sitemap-index.xml
```

**默认不屏蔽任何 AI 爬虫**。理由：Rutgers/Wharton 2026 年 4 月的研究发现，用 robots.txt 屏蔽 AI 爬虫的新闻站在六周内损失约 7% 周流量，且这是真人浏览数据而非爬虫计数。屏蔽 AI 抓取会连带损失可见度。若日后要屏蔽，在这里加 `GPTBot` / `ClaudeBot` / `PerplexityBot` 的 `Disallow`，但要清楚代价。

### 7.4 llms.txt：做，但别指望它引流

**实测数据（2026 年）**：Ahrefs 统计 13.7 万域名的服务器日志，**97% 的 llms.txt 在 2026 年 5 月收到零请求**；AI 检索爬虫只占这些文件请求量的 1.1%（GPTBot 4.51%、ClaudeBot 0.80%）。EZY 的 12 周日志研究里，OpenAI 读 robots.txt 3990 次、读 llms.txt 7 次。唯一例外是 Meta-ExternalAgent（193 次 vs robots.txt 172 次）。

Google 明确说 llms.txt「不会正面也不会负面影响你的可见度或排名」。

**结论**：写一份，成本几乎为零，作用是**给自主 agent 一张站点地图**（agent readiness），不是 SEO 手段。内容是纯 Markdown 的站点结构与要点，别把它当营销文案。

```text
# {{BRAND_NAME}}

> 上传一张宠物日常照片，几分钟拿到身份证、电影海报、时光画册与 AI 肖像。
> 图文创作、AI 肖像、视频短片、纪念空间共 10 种玩法，在微信小程序内完成。

## 主要页面
- [首页]({{SITE_URL}}/): 玩法总览与真实成品展示
- [文章]({{SITE_URL}}/blog/): 玩法教程、拍照技巧、产品设计取舍
- [用户协议]({{SITE_URL}}/legal/terms/)
- [隐私政策]({{SITE_URL}}/legal/privacy/)

## 玩法
- 宠物身份证: 正脸照 1 张生成证件卡，约 1 分钟
- 宠物电影海报: 日常照 1–3 张排成主视觉海报
- 宠物时光画册: 照片 6–20 张装订成长图与 PDF
- AI 宠物肖像: 四种风格预设一次出四张候选
- 星尘纪念: 纪念册、纪念视频、纪念页、成长对比图

## 说明
- 照片仅用于生成，可随时删除
- 纪念空间的陪伴天数是过去式且不递增（「陪伴了 N 天」）
```

**内容原则**：写事实与站点结构，不写营销话术。它的读者是自主 agent，需要的是准确的页面清单与产品要点。文章多了以后要不要逐篇列出，看维护成本 —— sitemap 已经承担了完整清单的职责，llms.txt 只需给主干。

**任何把 llms.txt 说成能提升 AI 引用的说法都超出了当前证据。**

### 7.5 内容层面（这才是真正的杠杆）

Google 的指南把重点全放在内容上，几条与本项目直接相关：

- **要有第一手观点**。「7 个新手养猫技巧」这类通用内容 Google 归为 commodity content，明确不推荐。我们的优势是真实产出 —— 文章应该基于实际生成结果与踩过的坑写，比如「为什么风格对比图必须用同一只猫」这种只有做过才知道的事。
- **不要为查询变体单独开页**。按 query fan-out 批量生成页面命中「规模化内容滥用」政策。
- **标题层级清晰、语义 HTML**。原型的 heading 层级已审过（h1 唯一、无跳级），文章页要保持。
- **图文并重**。文章配真实成品图，不用图库图。

### 7.6 内链与转化路径

文章模块的价值不只是被抓取，还要把搜索流量导向转化。三条：

1. **首页加文章入口**。原型的 11 区块里没有文章链接，顶栏菜单也没有。至少要在顶栏菜单加「文章」一项、页脚「关于」栏加一条 —— 否则文章是孤岛，搜索引擎能抓到但站内权重传不过去。
2. **文章页底部放 CTA**。复用首页第 9 区块的小程序码面板（`Cta.astro` 组件），从「看完教程」直接接到「扫码去做」。这是搜索流量的唯一变现路径。
3. **文章之间互链**。写玩法教程时链到相关玩法的其他文章。这需要人工维护，但 `reference('posts')` 可以在 frontmatter 里声明关联并做构建期校验 —— 引用了不存在的 slug 会在构建时报错，不会留死链。

**顶栏菜单加「文章」意味着导航项从 7 个变 8 个**。移动面板的逐项入场 delay 现在写到 `nth-child(7)`，加一项要补第 8 条（`.75s`）。这是 `src/config/site.ts` 集中导航项之后顺带解决的问题 —— 两个菜单从同一个数组渲染，不会漏。

### 7.7 性能（原型已达标，迁移后要复验）

原型实测：FCP 112–148ms、CLS 0、29 张图全带固有尺寸、26 张 lazy。迁移后必须复验，尤其：

- **`<img>` 的 `width`/`height` 不能丢**。Astro 的 `<Image />` 组件会自动加，但从原型搬过去的静态 `<img>` 要保留属性。
- **踩坑复述**：给 `<img>` 加了 `width`/`height` 属性后，任何只设 `width` 不设 `height` 的 CSS 规则会让属性高度生效、`aspect-ratio` 静默失效。原型里 `.media-frame img` 与 `.clay-frame img` 已加 `height: auto`，搬 CSS 时不要漏。
- hero 视频 3.51MB 是首屏最大单项。`preload="metadata"` 对它无效（`autoplay` 会覆盖），体积是唯一杠杆。

## 8. 部署

### 构建产物

在 `apps/website/` 下执行 `pnpm build`，产出 `dist/`，纯静态文件（HTML + CSS + JS + assets）。不需要 Node 运行时。

> **本仓库不是 pnpm workspace** —— 没有根 `package.json` 也没有 `pnpm-workspace.yaml`，`apps/platform` 与 `apps/miniprogram` 各自独立 `pnpm install`。因此**不能用 `pnpm --filter website`**，一律 `cd apps/website && pnpm <cmd>`，与现有两个应用同一个约定（CI 里也是靠 `working-directory` 分目录）。

### Nginx 配置

新增一个 server 块，与现有 `deploy/nginx/petbaby.conf` 并列。要点：

```nginx
server {
    listen 443 ssl http2;
    server_name {{SITE_URL}};
    root /srv/petbaby-website/current;   # 指向 dist/ 的软链
    index index.html;

    # trailingSlash: 'always' 对应的重写规则
    location / {
        try_files $uri $uri/index.html =404;
    }

    # 素材长缓存：文件名不带哈希，靠 assets/ 前缀整体给较短的 max-age
    location /assets/ {
        expires 7d;
        add_header Cache-Control "public, max-age=604800";
    }

    # HTML 不缓存，保证发布后立即生效
    location ~* \.html$ {
        add_header Cache-Control "no-cache, must-revalidate";
    }

    error_page 404 /404.html;
}

# www 301 到主域（择一为规范域）
server {
    listen 443 ssl http2;
    server_name www.{{SITE_URL}};
    return 301 https://{{SITE_URL}}$request_uri;
}
```

**`/assets/` 只给 7 天而非一年**，因为原型的素材文件名不带内容哈希（`work-golden.jpg` 这种）。换图后文件名不变，长缓存会让用户看到旧图。若日后给素材加哈希文件名，可以延长到一年。

### 发布脚本

新增 `deploy/scripts/release-website.sh`，与现有脚本同构（复用 `lib.sh` 的 `log` / `warn` / `fail` / `resolve_mode`）：

```
1. 拉代码（--ff-only，连同 release.sh 对权限位差异的处理一起照搬）
2. cd apps/website && pnpm install --frozen-lockfile && pnpm build
3. 原子切换：dist/ → /srv/petbaby-website/releases/<时间戳>/，再改 current 软链
4. 校验：curl 首页与 /blog/、抽查一张素材取到字节、sitemap 可解析
5. 保留最近 5 个 release 供回滚
```

**原子切换 + 软链**是关键：直接 `rsync` 到 `current/` 会有几秒的半新半旧状态。切软链是瞬时的，回滚也只是把软链指回上一个目录。

**与 platform 的发布完全解耦**：官网发布不碰 Docker、不重启容器、不跑数据库迁移。

### CI

在 `.github/workflows/ci.yml` 加一个 `website` job，与现有 `miniprogram` job 同构：

```yaml
website:
  runs-on: ubuntu-latest
  defaults:
    run: { working-directory: apps/website }
  steps:
    - uses: actions/checkout@v4
    - uses: pnpm/action-setup@v4
      with: { version: 10.13.1 }          # 与其余三个 job 一致
    - uses: actions/setup-node@v4
      with: { node-version: 22, cache: pnpm, cache-dependency-path: apps/website/pnpm-lock.yaml }
    - run: pnpm install --frozen-lockfile
    - run: pnpm build                      # schema 校验 + Astro 编译，任一文章 frontmatter 出错就挂
    - run: pnpm check:links                # 站内链接与 sitemap 的 URL 必须都能命中产物文件
```

**Node 版本要留意**：Astro 7 要求 **≥ 22.12.0**，且明确不支持奇数版本（v23 之类）。CI 现在写的是 `node-version: 22`，会解析到最新 22.x，满足要求 —— 但如果哪天有人把它钉到 `22.0.0` 就会装不上，这条约束在 `package.json` 里用 `engines` 声明一遍更稳。

链接检查值得做：文章多了以后互相引用，改 slug 很容易留死链，而静态站的死链不会有任何运行时报错。

## 9. 应用挪到 app. 子域的连带改动

主域给官网，`apps/platform` 挪到 `app.{{SITE_URL}}`。这不是官网侧的工作，但**漏了会出故障**，列在这里：

### 11.1 法务页与备案的占位口径

两项都先用占位，但**占位方式必须让人一眼看出是未完成的**，不能写成像正式条款的样子 —— 半真半假的隐私政策比空页面风险更高（用户会当它是承诺，而它没经过法务审核）。

**法务两页**（`/legal/terms/`、`/legal/privacy/`）：页面骨架、路由、导航链接全部做出来，正文放**结构化的章节骨架 + 明显的未完成标记**：

```
┌────────────────────────────────────────┐
│  ⚠ 本页内容尚未定稿，不构成任何承诺或   │  ← 顶部醒目提示条，
│    法律文件。正式版本发布前请勿依赖。    │     用 --primary 描边 + 浅底
└────────────────────────────────────────┘

用户协议（草案骨架）

1. 服务说明          ← 每节只写小标题 + 一句「待补充」
2. 账号与使用规范
3. 内容与知识产权     ← 这节要点：用户上传照片的授权范围、生成内容的权属
4. 付费与退款
5. 照片与数据处理     ← 与隐私政策呼应：仅用于生成、可随时删除
6. 免责声明
7. 争议解决
```

章节骨架不是凑数 —— 它把「需要法务回答哪些问题」列清楚了，交给法务时是一份需求清单而非空白页。第 3、5 节标了要点，因为这两条与产品设计直接绑定（原型信任条已经对外说了「照片仅用于生成，可随时删除」，正式条款必须与之一致，否则是虚假宣传）。

**页脚链接照常指向这两页**，不再是死链。`data-placeholder="legal-terms"` / `legal-privacy` 标记，收口时 grep 得到。

**备案号**：页脚底部版权行右侧留位置，`data-placeholder="icp-record"`，占位文字「ICP 备案号待补充」。备案下来后替换成真实号码并按要求链到 `https://beian.miit.gov.cn/`。

> **上线前必须确认的两件事**（占位不等于可以忘）：
> 1. 备案是国内服务器托管的**前置条件**，没有备案域名解析不了 —— 这项不做完根本上不了线，占位只是让代码先跑通
> 2. 法务正文必须在**面向真实用户开放前**替换。内部预览、给同事看不受影响

**这两项我无法代办**，需要你走流程。第 1 项你生成小程序码即可。

## 13. 实施顺序

分四步，每步可独立验证：

| 步 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 搭 Astro 骨架，首页拆成 11 组件，CSS/JS/assets 原样搬入 | 与 `prototype/index.html` **逐像素比对三档断点**；CLS 仍为 0；hero 视频行为不变 |
| 2 | 小程序码三触点：`QrPopover.astro` + 顶栏按钮 + 右下角悬浮 | 桌面悬停/触屏点击都能开关；Tab 可达、Esc 关闭且焦点返还；hero 内与 CTA 区不显示悬浮按钮；reduced-motion 下无动画 |
| 3 | 接 SEO 基础设施：`Seo.astro`、JSON-LD、sitemap、robots.txt、llms.txt、canonical | sitemap 可解析且 URL 与 canonical 逐字一致；结构化数据过 Google Rich Results Test |
| 4 | 文章模块：collections schema、列表/详情/标签/分页、RSS、404 | 放 2 篇真实文章跑通；故意写错 frontmatter 应在构建时报错；正文列表有符号、行内链接有下划线 |
| 5 | 法务两页 + 备案占位 + 顶栏 solid 变体 | 页脚链接不再是死链；solid 顶栏在浅底上可读（实测对比度）；未定稿提示条醒目 |
| 6 | 部署：Nginx 配置、`release-website.sh`、CI job | staging 走通一次发布 + 回滚；死链检查通过 |

**第 1 步的验收标准是逐像素比对**，这是「与原型完全一致」这个要求的落地方式。用 Playwright 截三档全页图，与原型的截图做像素级 diff —— 拆组件时漏一个 class 或改一层嵌套，肉眼未必看出来，diff 会。

**第 2 步单独列一步而不是并进第 1 步**：它改的是原型没有的交互（悬停弹框、悬浮按钮、IO 显隐规则），会新增 DOM 与 z-index 层级。放在逐像素比对通过之后做，比对基线才干净 —— 否则首页多了两个按钮，diff 会全红，看不出是哪里的偏差。

第 2 步做完要**重跑一次首屏性能核验**：悬浮按钮是 `position: fixed` 元素，加不当会引入 CLS；二维码图（≥430×430 PNG）三处引用，要确认它没有被 eager 加载拖慢首屏（应为 `lazy`，弹框展开时才需要）。
