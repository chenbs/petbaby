## 摘要（结论先行）

1. **现有代码的组件化程度远高于方案的预期。** 16 个 `t-*` 公共组件 + 4 套主题 + 56 个语义
   token，页面里零硬编码（有 `pnpm validate` 八项门禁强制）。方案里「阶段 1 新建
   `styles/tokens-structure.wxss`」「阶段 2 重建卡片/按钮/输入/步骤条/空状态」这两步
   **不应按新建执行，而应按扩参改造执行** —— 组件结构已经对了，缺的是参数取值。
2. **有一条硬技术约束，必须先解决再谈第二章。** glass 主题的 CSS 变量注入串已经
   **2045 / 2048 字节**，只剩 3 字节。方案第二章的结构 token 若按主题 token 追加，
   门禁立刻挂。正确做法是全部进 `CONSTANT_VARS`（只在 `app.wxss` 声明一次，不进注入串）。
   详见 [第七章 冲突 1](#冲突-1token-放哪里glass-只剩-3-字节)。
3. **方案的头号价值主张（功能入口换真实成品图）目前无数据可依。** 玩法 manifest
   （`apps/platform/src/plugins/registry.ts`）没有任何样例图字段，`/api/plugins`
   返回里也没有。这不是小程序侧改样式能解决的，需要跨仓改动 manifest + Zod schema +
   后台上传。**这是 A / C / E 三个方向的真实阻塞点，比"图还没拍"更靠前一层。**
4. **两个页面已经是 C 方向了。** `pages/work` 和 `pages/ai-run` 已用
   `navigationStyle: custom` + `components/glass-sheet/`（含 WXS 手势、三档吸附、
   亮度联动、视频背景、降级），完成度高于方案 C 的描述。这两页不需要重做。
5. **主基调建议选「精致」（F 的排版方法论），骨架选 A，J 只用在结果页与空状态。**
   理由见 [第六章](#六六个待决策项的建议)。核心是：J 作主基调会与现有 4 套皮肤中的
   3 套（glass / light / dark）人格直接冲突，而 F 的方法论（字重对比、负字距、留白）
   能表达成 token，对四套皮肤同时生效。

### 路由结构

`custom-tab-bar/` 已存在并自行订阅 ThemeManager）。其余 19 页全是 `navigateTo` 二级页。

三条创建链路都是 **配置页 → `redirectTo` 运行页** 的两段式：

```

               ├─→ memorials ──→（衍生品 action-sheet）
               └─→ commerce ──→ physical
```

`work` 是五条链路的共同汇聚点，改造它的收益按路径数放大 5 倍。
`me` 是 9 个长尾页的唯一入口。

## 二、现有 Token 盘点

### 2.1 四层结构与文件位置

| 层 | 文件 | 职责 |
|---|---|---|
| L0 真源 | `theme/tokens.js` | `TOKEN_SPEC` = 56 个 token 的**键名 + 类型**真源；`CONSTANT_VARS`；`deriveScale()` |
| L1 调色板 | `theme/themes/*.js` 内的 `palette` | 每套皮肤私有，页面**不可**引用 |
| L2 语义 token | 同文件的 `tokens` | 页面唯一可引用层 |
| L3 派生 | `tokens.js` 的 `deriveScale()` | 由 L2 算出间距阶、字阶等 |

装配与分发：`theme/index.js`（`THEMES` 数组 + `resolveTokens()`）→
`theme/manager.js`（单例、缓存、广播、导航栏）→ `theme/page-mixin.js`（22 页全接入）。

### 2.2 命名规范

**camelCase → kebab-case 自动转换**，由 `tokens.toCssVarName()` 完成：
`cardRadiusVariant` → `--card-radius-variant`。所以：

> **新增 token 只能写自然 camelCase 名，不能自己起 `--c-xxx` 这种 CSS 名。**
> 方案 2.7 建议的 `--c-skeleton` / `--c-divider-soft` / `--c-clay-base` 不符合本规范，
> 应改成 `skeletonBase` / `dividerSoft` / `clayBase`。

### 2.3 主题切换机制

`app.js` 的 `onLaunch` 里 `manager.init()`（**早于任何网络请求**，避免首屏闪变）→
读 `wx.getStorageSync('petbaby_theme')` → 校验 → 探测 `backdrop-filter` 支持度。

切换（`setTheme`）只走：内存 → `setStorageSync` → `wx.setNavigationBarColor` →
广播。**零网络请求。** 广播同时遍历 `getCurrentPages()` 调每页的 `__applyTheme`，
所以返回上级页不残留旧主题。

变量下发靠 `<page-meta page-style="{{themeStyle}}">`，因此**基础库下限 2.9.0**。
组件不在 page 节点下拿不到变量，`custom-tab-bar` 和 `glass-sheet` 各自订阅 manager。

**降级**：`detectBlurSupport()` 按平台/基础库推断（Android 需基础库 2.10+ 且系统 ≥10），
`false` 时 `resolveTokens()` 叠加皮肤的 `degrade` 对象。**这套机制已经覆盖了方案 C 落地
要点里的 `@supports` 降级，且更强**（JS 侧可控 + 降级态也过对比度门禁）。

### 2.4 已有槽位 vs 方案第二章要求

| 方案章节 | 现状 | 缺口 |
|---|---|---|
| 2.1 间距 | ✅ `deriveScale()` 产出 `--space-1..8`，取值与方案**完全一致**（8/16/24/32/48/64/96/128） | 缺 `--page-x-wide`、`--gap-item/group/section` 语义别名 |
| 2.2 圆角 | ⚠️ 只有 `--card-radius`、`--card-radius-variant`、`--button-radius`、`--radius-pill` | **缺完整 xs→xl 阶梯。方案说"现有所有卡片同一圆角是粗糙感来源"—— 这条属实** |
| 2.3 字阶 | ⚠️ 有 `--title-size`/`--font-h2`/`--font-h3`/`--body-size`/`--small-size`/`--eyebrow-size`、`--title-weight`、`--title-letter-spacing` | **缺行高 token（全部硬写在 wxss 里）、缺 `--fw-*` 字重阶梯、缺 `--ls-tight/tighter/kicker/cover`** |
| 2.4 阴影 | ⚠️ 只有 `--card-shadow` 单槽 + `--glass-shadow` | **缺 `--shadow-image/float/press/clay`。且现有卡片确实靠 `--card-border` 分层 —— 方案的诊断准确** |
| 2.5 图片 | ❌ 无 | 缺全部 `--ratio-*`、`--overlay-img`、暗角 |
| 2.6 动效 | ⚠️ 有 `--transition-duration`、`--transition-easing`、`animationType`（4 形态）、`--glass-easing` | 缺 `--dur-fast/slow/reveal`、`--stagger` |
| 2.7 语义色 | ⚠️ 有 `--divider`、`--success/warning/error`、`--*-surface`、`--ai-gradient*` | 缺 `skeletonBase`/`skeletonShine`/`dividerSoft`；clay 与 cover 两组待主基调定案 |

**结论**：间距层已完全达标，动效与语义色接近达标，**圆角阶梯、行高/字重/字距、阴影分层、
图片规则**是四块真缺口 —— 恰好也是方案认定的「质感载体」。

### 2.5 门禁（`scripts/validate.js`，八项）

改样式绕不开这八条，前三条最常撞：

1. 每页 4 文件齐备
2. 全部 JSON 可解析
3. **零硬编码扫描**：`.wxss` 里出现 hex / `rgba()` / 颜色关键字即失败；
   `border-radius`/`box-shadow`/`font-size`/`padding`/`margin`/`gap`/`letter-spacing`
   的值必须含 `var()` 或 `calc()`，否则失败。**`app.wxss` 是唯一豁免文件。**
4. Token 完整性：四套皮肤逐一比对 `TOKEN_SPEC` 键名与类型
5. 文字对比度：4 组检查 × 4 皮肤 × 降级态
6. 玻璃面板对比度：纯白/纯黑底图 × 两档 × 降级态
7. **注入串 ≤ 2048 字节**（见下）
8. **`var()` 引用必须有来源** —— 笔误变量会被抓出来（无来源的 `var()` 只静默失效）

### 2.6 注入串余量（本轮实测）

```
cute  1834 / 2048      light 1764 / 2048
glass 2045 / 2048  ←   dark  1823 / 2048
```

**glass 只剩 3 字节。** 这是第二章落地方式的决定性约束，见 [冲突 1](#冲突-1token-放哪里glass-只剩-3-字节)。

## 三、组件盘点

`components/` 下 16 个 `t-*` 组件 + `shared.wxss`（组件内文本类，因
`styleIsolation: isolated` 使 `app.wxss` 不下渗）+ 根目录 `custom-tab-bar/`。

| 组件 | 现有能力 | 对照方案第三章 | 处置 |
|---|---|---|---|

| `t-steps` | 数字圆圈 + 全部文字标签 | 方案要 N 段细线 + 只显示当前步名 | **改 WXML/WXSS**，属性不变（只 `create` 一页用） |
| `t-empty` | emoji + 标题 + 描述 + CTA + `decor` | 方案要单色线条 SVG、禁 emoji | **改绘制方式**，见 [冲突 5](#冲突-5空状态插画的载体) |
| `t-skeleton` | card/list/grid/text × count | 方案 3.7 要求形状与内容一致 + 微光 1400ms | ✅ 已达标，补 `skeletonBase/Shine` token |
| `t-photo-grid` | 选序号、addable、manageable、reorderable、预览、`columns` | 方案 3.3 card-select 的基础 | ✅ 复用，加固定比例容器 |
| `t-glass-sheet` | 三档吸附 + WXS 零 setData 拖动 + 亮度联动 + 视频背景 + 降级 | **超出方案 C 的描述** | ✅ 不动 |
| `t-navbar` | 状态栏适配、`transparent`、`tone=inverse` | 方案沉浸式页需要 | ✅ 复用 |
| `t-progress` | bar / ring（conic-gradient）、`tone` | 方案未列，`me`/`commerce`/`video` 在用 | ✅ 保留 |
| `t-tag` `t-notice` `t-dialog` `t-popup` `t-action-sheet` `t-loading` | 齐全，均已主题化 | 方案未列 | ✅ 保留，跟随新 token |
| `custom-tab-bar` | 已 custom、自订阅主题、3 tab、`anim-*` | 方案 3.4 要悬浮胶囊 + 取消色块高亮 | **改 WXSS 形态**，逻辑不动 |

### 组件化程度评估

- **优秀**：所有页面已无原生 `<button type="primary">`、无 `wx.showModal`，
  提示条/弹窗/操作面板/骨架屏全部走组件。
- **一致性**：4 种 `anim` 形态（bounce/glow/fade/neon）由页面透传 `animType`
  贯穿全部组件的 `:active` 反馈 —— 方案 2.6「按压缩放」已有落点，只需改取值。
- **需新建的只有 2 个**：`t-chip-group`、`t-card-select`。方案阶段 2 的「重建」
  实际是「扩参 + 换绘制」，工作量比方案预估低。
- **页面内联样式仍有重复**：`.option` / `.scene` / `.bgm-option` / `.swatch` 这类
  选项块在 `ai-create`、`interactive-create`、`video-create` 各写一遍，
  正是 `t-chip-group` / `t-card-select` 该收口的部分。

## 六、六个待决策项的建议

### 1. 主基调：可爱 vs 精致 → **建议「精致」（F 的排版方法论）**

决定性理由是现有代码事实：**项目已有 4 套皮肤，其中 3 套的人格是克制的** ——
`glass`「AI 未来感」、`light`「专业克制」、`dark`「夜间沉浸」，只有默认的 `cute`
是「陪伴治愈」。

若选 J 作主基调，要么把 4 套皮肤全部改成黏土（那 `light`「专业克制」就不存在了），
要么让 J 只在 `cute` 下生效（那就不是主基调，而是皮肤特性）。**两条都是退化。**

反过来，F 的方法论（字重对比、负字距、留白纪律、去装饰）能表达成 token，
对四套皮肤同时生效，且与 `light`/`dark`/`glass` 的既有人格一致，
对 `cute` 也只是「更克制的可爱」而非否定。

J 保留在三处局部（结果页 / 空态 / `growth` 入口卡），可爱度在情绪高点释放。
这正是方案 499 行给出的「选精致」路线。

### 2. 骨架：A 还是 E → **建议 A，E 作为区块嵌入 `me` 与 `pets`**

三条理由：

- **E 的空态风险在本项目是实的**。`pets` 页现在的空态文案是「做第一件作品时会顺手建好
  档案」—— 也就是说**用户是先做作品、后有宠物档案的**。E 要求「进入即看到某只宠物的主页」，
  与这个既有获取顺序相反，新用户首屏会是空的。
- **A 的通用性在本项目被 7 个高密度页面需要**。`commerce` 一页就有 5 个并列区块，
  E 的结构承载不了。
- **E 的数据还不存在**：宠物封面图、作品数、照片数都没有现成字段。A 只需要样例图。

E 的价值（情感联结、陪伴天数）建议以区块形式嵌入 `me`（替换现在的额度环区）
和 `pets`（每张档案卡加陪伴天数），成本远低于整页改 E。

### 3. 页面分配 → 见[第四章](#四方向分配建议)

需你确认的是第 17 项 `memorials`：**对已离开的宠物显示「陪伴第 N 天」是否恰当**。
我倾向于在 `mood: memorial` 下改成「陪伴了 N 天」（过去式），
或者干脆不显示数字。这是产品判断，不是技术判断。

### 4. Token 兼容策略 → **建议全部进 `CONSTANT_VARS`，不新建 wxss 文件**

方案说新建 `styles/tokens-structure.wxss`。**本项目不能这么做**，两条原因：

- `validate.js` 只豁免 `app.wxss` 一个文件。新 wxss 里写 `rgba(60,35,20,.28)` 会被规则 3 拒。
- glass 注入串只剩 3 字节，结构 token 若进 `TOKEN_SPEC` 会撞规则 7。

正确做法：结构常量（阴影配方、圆角阶梯、比例、缓动、时长、字距）**与主题无关**，
按现有架构应登记到 `tokens.js` 的 `CONSTANT_VARS`，由 `app.wxss` 的 `page{}`
声明一次。规则 8 会校验两处取值一致，笔误也拦得住。**这条路已有 3 个先例**
（`--radius-pill`、`--glass-easing`、`--glass-blur-degraded`）。

只有**真正随皮肤变化**的少数几个（如暗色主题的 `--shadow-hue` 从暖褐改纯黑、
`borderHighlight`）才进 `TOKEN_SPEC` —— 而这几个进去之前，glass 必须先腾出字节。

### 5. 样例图生产 → 建议顺序：**先解决数据字段，再拍图**

`registry.ts` 的 manifest 没有样例图字段，`/api/plugins` 也不返回。所以即使图今天
就位，小程序也拿不到。建议的最小改动链：

1. `apps/platform/src/plugins/registry.ts`：manifest 加 `samples: { hero, grid[] }`
2. 同步改 `runtime.ts` 里校验 manifest 的 Zod schema（否则新字段会被 Zod 拒）
3. `plugin_configs` 是数据库驱动的，已有 seed 逻辑，加字段后需确认播种/版本兼容
4. 后台加样例图上传（`src/app/admin/**`）

**这条链路的工作量与前端改造相当，且必须先完成。** 建议现在排期。

### 6. 渐进替换 vs 整体重做 → **渐进替换，理由充分**

现有代码组件化程度高、零硬编码、有八项门禁。整体重做会丢掉 `t-glass-sheet`
的 WXS 零 setData 手势、四套皮肤的对比度已验证结论、以及 22 页的门禁合规状态。

渐进路径明确：token 层（1 处）→ 组件层（16 处）→ 页面层（按需）。
组件层改完，22 页自动继承新观感，这是本项目独有的杠杆。

## 七、方案与现有代码的冲突（需先解决）

这七条是读完代码后新发现的，方案文档里没有。**前 3 条会直接导致 `pnpm validate` 失败。**

### 冲突 1：token 放哪里（glass 只剩 3 字节）

- **方案**：新建 `styles/tokens-structure.wxss`，在 `page, .page{}` 里声明结构 token。
- **现实**：`validate.js` 规则 3 只豁免 `app.wxss`；规则 7 限注入串 ≤2048，glass 已 2045。
- **处置**：结构常量进 `tokens.js` 的 `CONSTANT_VARS` + `app.wxss` 声明（规则 8 会校验一致性）。
  随皮肤变化的少数 token 进 `TOKEN_SPEC`，**但需先为 glass 腾字节**
  （可行方向：缩短 glass 的 `background` 三段渐变写法，或把 `glassBackgroundSolid`
  这类降级专用值移出注入串）。

### 冲突 2：删 border 在 light / dark 上会丢层级

- **方案 3.1**：统一删除卡片的 `1rpx solid border`，暗色主题除外改 `--border-highlight`。
- **现实**：`light` 主题是 `background: #FFFFFF` + `cardBackground: #FFFFFF` ——
  **白底白卡，删掉 border 后卡片会完全消失**，现有 `--card-shadow` 只有
  `0 2rpx 8rpx rgba(17,17,17,.06)`，撑不起分离。
- **处置**：`light` 必须靠新的 `--shadow-card`（方案 2.4 的双层暖褐）建立分离，
  且 `cardBackground` 或 `background` 二者之一要偏移一档。这是**改 token 取值**，
  会触发规则 5 对比度重算。`dark` 保留 `borderHighlight`。

### 冲突 3：`rgba(var(--shadow-hue), .10)` 这种写法过不了门禁

- **方案 2.4**：`--shadow-hue: 60, 35, 20;` 然后 `rgba(var(--shadow-hue), .10)`。
- **现实**：规则 3 的正则 `/\brgba?\s*\(/` 会命中 `.wxss` 里的 `rgba(`，无论参数是不是变量。
- **处置**：阴影配方必须作为**完整成品值**放在 `CONSTANT_VARS` 或主题 JS 里，
  `.wxss` 只允许出现 `box-shadow: var(--shadow-card)`。色相拆分只能在 JS 侧做字符串拼接。

### 冲突 4：`@supports` 降级与现有机制重复

- **方案 C 落地要点**：用 `@supports (backdrop-filter: blur(20px))` 做降级。
- **现实**：`manager.detectBlurSupport()` 已在 JS 侧判定并叠加皮肤 `degrade`，
  且**降级态也过规则 5/6 的对比度门禁** —— 比 CSS 侧 `@supports` 更强（`@supports`
  判定通过但性能差的机型仍会卡）。
- **处置**：不引入 `@supports`，继续用现有机制。新增的半透明层一律走
  `blurOk` 页面变量透传。

### 冲突 5：空状态插画的载体

- **方案 3.6**：改单色线条 SVG，240×240rpx，颜色跟随 token，禁用 emoji。
- **现实**：小程序 `.wxss` 不能外链 SVG 作背景图；本地 `.svg` 文件会增加主包体积；
  base64 data URI 里的 `#` 与 `fill` 颜色会被规则 3 的 hex 正则命中，且**颜色写死在
  data URI 里无法跟随主题**。
- **处置**：用**纯 CSS 绘制线条图形**（`border` + `border-radius` + 伪元素），
  颜色吃 `var(--text-secondary)`，随主题自动变。项目里已有先例：
  `growth` 页的三个视觉块（`.quad` / `.dust` / `.film-frame`）、`index` 的 `.seal`
  都是纯 CSS 画的，路子已经验证过。方案「禁 emoji」的目标能达成，
  「SVG」这个载体换掉。

### 冲突 6：`me` 页整页改 E 会与 tabbar 语义冲突

`me` 是 tab 3，承载 9 个长尾入口 + 额度 + 通知。E 要求「进入即对象主页」，
但对象主页属于 `pets`（tab 外的二级页）。整页改 E 会让 `me` 和 `pets` 职责重叠。
**处置**：`me` 只嵌入 E 的统计条形态，对象主页留在 `pets`。

### 冲突 7：两处「色块」不能改缩略图

方案 3.3 硬规则「凡描述视觉结果的选项必须用缩略图」，有两处例外：

- **`theme` 页的 4 张预览卡**：必须吃自身 `style` 变量渲染，这才是主题的真实观感。
  换成缩略图反而失真。
- **`interactive-create` / `interactive` 的场景色卡**：场景配色是**内容属性**，
  由 `theme/scene-presets.js` 内联注入，刻意与全局 token 隔离
  （`validate.js` 第 197 行有注释说明）。色块就是它的准确表达。

真正该改的是 **`ai-create` 的 `.swatch`**（风格预览用抽象渐变色块）——
这一处是方案诊断的典型违例，必须换同一只样板宠物的对比缩略图。

## 八、拍板结论（2026-07-30 已定）

第六章的建议全部获准，另加两条范围决定。以下是**已生效的执行依据**，
与上文「建议」性质不同 —— 上文留作决策过程记录，本节才是实际落地口径。

| 决策项 | 结论 | 落点 |
|---|---|---|
| 主基调 | **精致**（F 的排版方法论，非整屏 F） | 字重/负字距/留白进 token，四套皮肤同时生效 |
| 骨架 | **A**，E 作区块嵌入 | `index` 走 A；`pets` / `me` 嵌 E 区块 |
| 结构 token 位置 | **全部进 `CONSTANT_VARS`** | 只在 `app.wxss` 声明一次，不进注入串，绕开 glass 的 3 字节余量 |
| J 的落点 | **限 3 处**，只抽质感层 | 结果卡、空状态、`create` 结果区 |
| 纪念页陪伴天数 | **过去式且不递增** | 「陪伴了 N 天」，截止日锁在离开日期 |
| 范围 | **全做完**，不分批停 | 交接说明里「每页停下等截图」的约定本轮不适用 |

### 纪念页过去式的实现约束

「不递增」不是文案问题，是取数问题：天数必须有**固定截止日**，
否则「陪伴了 N 天」每天继续往上涨，而对这一页的用户来说那件事已经结束。

`pets` 表没有离开日期列。实现取 `memorial_spaces.created_at` 的最小值：
`createMemorialSpace` 在建空间的同一次调用里把 `life_stage` 改成 `memorial`，
两者本是同一次操作写下的，所以这个时间就是陪伴结束那天。
经 `listPets` 以 `memorialSince` 下发，端上 `services/companion.js` 用它封口。

不新增列的理由：加列要回填历史数据，而事实已经能从既有数据推出来。

## 九、生图接入（素材生产链路）

方案的头号价值主张是「功能入口换真实成品图」（摘要第 3 点）。
素材不能靠占位图糊过去 —— `LocalImageProvider` 产出的是纯色 SVG + 文字，
正是方案 3.3 点名的抽象色块违例，挂上去比留空更糟：看着像真样例，实际不给任何判断依据。

### 工具链位置

`tools/imagegen/`，独立于两个 app，不进构建产物：

| 文件 | 职责 |
|---|---|
| `client.mjs` | lingsuan 客户端（generations + edits，url/b64 统一、退避重试、300s 超时） |
| `prompts.mjs` | 提示词库：样板宠物、源照片、风格、玩法、玩法入口图 |
| `crop.mjs` | sharp 按方案 2.5 的固定比例裁切（接口忽略 size 参数，必须自己裁） |
| `generate.mjs` | CLI 编排 + 断点续跑（单张 45s，批量要能中断恢复） |
| `upload-samples.mjs` | 推对象存储并打印可粘进 `registry.ts` 的 manifest 片段 |

### 凭据来源

`LINGSUAN_IMAGE_API_KEY` / `LINGSUAN_IMAGE_BASE_URL`，见 `.env.example` 与
[环境变量参考](../delivery/04-environment-reference.md)。
仅 `tools/imagegen` 与运行时 `HttpImageProvider` 读取，小程序侧不接触。

### 样板宠物的硬规则

风格对比图**必须同一只主体**（方案 3.3）。换了宠物，用户比较的就是宠物而不是风格。

实现固定为橘白猫「摩奇」（`prompts.mjs` 的 `MODEL_PET`），
4 张风格图与多图玩法全部用它。风格 id 在三处必须一致：

- `prompts.mjs` 的 `AI_STYLES`
- `apps/platform` 的 `AI_STYLE_IDS`（单一事实来源，`growth-service.ts` 导出）
- `apps/miniprogram` 的 `ai-create.js` 里 `STYLES`

错配不抛异常 —— 端上按 id 取图，取不到就退回纯文字选项，线上只表现为「缩略图不见了」。
`registry.test.ts` 有一条断言把 manifest 的键钉在枚举上。

### 样例图下发路径

`registry.ts` 存**站内相对路径**，`/api/plugins` 出口按 `PUBLIC_APP_URL` 补绝对域名 ——
小程序 `<image src>` 遇到以 `/` 开头的值会当成主包内本地文件去找，必然裂图。

键名带内容哈希：样例图下发 immutable 长缓存，换图必须换键，否则 CDN 与客户端一直拿旧图。

老库回填按**逐键合并**：只补库里缺的键，已有值不动（那些是运营在后台改过的）。
不能按「有 samples 就跳过」处理 —— 那样后续新增的子键（如 `styleUrls`）
永远进不去已写过 `heroUrl` 的行。
