# 虚拟支付合规改造方案

更新：2026-08-05
状态：**方案待评审，未开工**。这是全局改造，与「宠物小岛」（`22` 号文）无关 —— 岛只是它的下游受益方之一。

## 0. 摘要

微信 2026-02-27 更新《小程序虚拟支付业务管理规范》，把虚拟支付从「iOS 受限」改为**全终端开放 + 强制合规**：**2026-04-01 起**，涉及虚拟商品的小程序须完成全终端（iOS / 安卓 / Windows / 鸿蒙）虚拟支付接入，未接入按违规处理，可风险提醒、限制功能，直至暂停或终止服务。

适用范围明确列举了 **VIP 会员、解锁功能、订阅内容、打赏、虚拟道具、AI 工具点数**等。我们现有的**会员**与**作品解锁**落在这个描述里，而当前实现走的是普通微信支付 v3 JSAPI（`server/payments/provider.ts` 的 `/v3/pay/transactions/jsapi`）。

**该截止日期已经过去，这是当前优先级最高的合规风险，高于任何新功能。**

盘点中另外发现一个与合规无关的既有缺陷，同样严重：**`growth_orders` 链路从未接入真实支付**（3.3）。会员、年度报告、健康档案三类订单的 `payGrowthOrder` 直接把状态改成 `paid` 并发放权益，**从不调用 `paymentProvider`** —— 生产环境下用户不付钱就能拿到会员。这条不是虚拟支付带来的，是既有实现的漏洞，但两件事要一起改。

一个重要的辩护空间，决定改造范围能压到多小（2.3）：我们卖的「解锁」交付的是**可下载的 PDF / 图片 / 视频文件**，可能被归为数字内容商品而非「解锁功能」；而**会员是站内权益，很难辩护**。这个边界必须去 MP 后台或工单确认，不能自行判断 —— 判定结果直接决定是「只改会员」还是「全线改造」。

## 1. 已核实的事实

以下取自微信官方文档，2026-08-05 抓取。**费率与政策会变，实施前必须复核。**

### 1.1 适用范围

小程序内所有**非实物商品**的购买与支付都须走虚拟支付。文档原文列举：虚拟货币、解锁功能、订阅内容、付费功能、打赏、购买虚拟礼物。规范更新公告进一步列举：VIP 会员、充值代币、录制课程、音视频内容、电子书、付费题库、付费咨询、**AI 工具点数**。

**外部导流被明确封堵**：不得引导用户跳转 APP、公众号、H5、个人号或外部网站完成支付。

### 1.2 开通条件

| 项 | 要求 | 我们的状况 |
| --- | --- | --- |
| 主体 | **已认证**的企业 / 事业单位 / 个体工商户，主体信息完备。个人号不可 | **需确认**（登记进 `04-external-prerequisites.md`） |
| 基础库 | 安卓 / 鸿蒙 / Windows 需 **2.19.2+** | 当前 `libVersion` 是 **2.9.0**，须抬升（4.1） |
| iOS 客户端 | 微信 **8.0.68+**，设备 **iOS 15+** | 用户侧条件，不可控，需降级路径（4.2） |
| iOS 账号 | App Store 账号须为**中国大陆** | 不可控 |
| iOS 单笔 | 最低 **1 元**，不足部分进代币余额 | 影响定价（4.3） |
| 开通流程 | 后台【虚拟支付】→ 签协议 → 提交商户资料 → 审核 **1–7 工作日** → 账户验证 → 扫码签约（1–2 工作日）→ 下发**新的子商户号** | 未开始 |
| iOS 额外 | Apple 支付是**独立开关**，默认关闭；须先配置并通过**小程序简称**审核（Apple 支付面板要显示 display name） | 未开始 |

### 1.3 费率与结算

| 端 | 标准费率 | 2026 限时 | 结算 |
| --- | --- | --- | --- |
| 安卓 / 鸿蒙 / Windows | 10%（会员订阅：首笔 1%，第二笔起 10%） | **1%** | T+3 分账 |
| iOS | **17%**（Apple 12% + 腾讯 5%） | **12%**（腾讯部分减免） | Apple 结算后 **30–60 天** |

对比现状：微信支付 v3 普通商户费率约 0.6%。**虚拟支付在 iOS 上的抽成是当前的 20 倍**，这个数字直接决定哪些东西值得卖（5.2）。

### 1.4 三个容易低估的运营约束

- **iOS 无沙箱。** 文档明确「不支持使用沙箱环境，仅支持使用现网环境」。测试要用真实 Apple ID 花真钱，只能靠低价商品 + 事后申请退款验证。这让 iOS 支付**无法进入自动化测试**，与仓库现有「E2E 覆盖完整支付链路」的做法冲突（4.5）。
- **iOS 退款不由我们发起。** 用户走 App Store 申诉，Apple 向我们发退款问询（最多三次），我们须通过 `xpay_subscribe_ios_refund_query_notify` 在 **3 秒内**响应 `result_code`（0 允许 / 1 拒绝）并附 `evidence` 审计字段。三次都超时则由 Apple 独自决定。**这是一套新的服务端接口，现有 `orders/[id]/refund` 的退款模型不适用。**
- **代币名称与兑换比例一经发布不可修改。** 若引入代币，命名要一次定对。**建议不引入代币**，直接按道具计价（5.3）。

### 1.5 未能核实的项（不要当成已确认）

- **规范原文在需登录的微信开放社区**，本文依据的是官方文档页 + 移动支付网 2026-03-02 报道，未读到公告原文。
- **「可下载文件」是否算「解锁功能」没有官方口径。** 这是 2.3 的核心问题，只能问。
- **类目要求**：费率表列了非游戏类目（工具、社交、深度合成、文娱），据此推断非游戏小程序可用，**但这是从费率表反推，不是明文的资格规则**。
- 是否需要额外许可证（如涉及特定内容类目），文档未提。

## 2. 现状盘点与风险判定

### 2.1 五处付费场景

| # | 场景 | 端上入口 | 接口 | 交付物 | 风险判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | 作品解锁（图文/画册/视频） | `pages/work/work.js:87` | `POST /api/orders` → `/prepare` → `wx.requestPayment` | **可下载文件**（图/PDF/视频） | 待确认（2.3） |
| 2 | AI 候选图解锁 | `pages/ai-run/ai-run.js:45` | `POST /api/ai-runs/[id]/unlock` → `/orders/[id]/prepare` | **可下载文件**（图） | 待确认 |
| 3 | **会员** | `pages/commerce/commerce.js:106` | `POST /api/memberships` → `/api/growth-orders/[id]/pay` | 站内权益（`tierUnlock` / `healthExportUnlimited`） | **高风险，几乎必然适用** |
| 4 | 年度报告高清版 | `pages/commerce/commerce.js:183` | `POST /api/growth-orders/[id]/pay` | 可下载文件 | 待确认 |
| 5 | 健康档案 PDF 单买 | `pages/health/health.js` | `POST /api/health-documents/orders` → `/pay` | 可下载文件 | 待确认 |
| — | 实体纪念品 | `pages/physical/physical.js:100` | `POST /api/physical-orders/[id]/pay` | **实物** | **不适用**，继续走普通微信支付 |

Web 端同构入口在 `components/ai-results-client.tsx`（走 `getBrandWCPayRequest` 公众号内支付）。

### 2.2 两条支付链路

```
链路 A（真实支付，已接微信支付 v3）
  POST /api/orders            → 建单
  POST /api/orders/[id]/prepare → paymentProvider.create() → clientParams
  端上 wx.requestPayment（或 Web 的 getBrandWCPayRequest）
  POST /api/payments/wechat/notify ← 微信回调
  场景 1、2、6

链路 B（growth_orders，从未接真实支付 —— 见 3.3）
  POST /api/memberships 等     → 建单
  POST /api/growth-orders/[id]/pay → 直接 UPDATE status='paid' 并发放权益
  场景 3、4、5
```

`payments/provider.ts` 的 `PaymentProvider` 接口只有 `create` / `refund` 两个方法，实现是 `WechatPaymentProvider` 与 `DevelopmentPaymentProvider`，由 `selectPaymentProvider()` 按运行模式选。**这个 provider 抽象是本次改造最大的资产** —— 虚拟支付可以作为第三个实现接进去（3.1）。

### 2.3 分界问题：可下载文件是否算「解锁功能」

这是整个改造的**范围决定项**，必须先有答案再动手。

**支持「不适用」的论据**：我们收的钱换来的是一个**可下载、可离线保存的文件**（PDF、PNG、MP4），用户下载后与小程序无关。这更像数字内容商品，而「解锁功能」的通常语义指站内功能开关。

**支持「适用」的论据**：文档列举里就有「解锁功能」「订阅内容」，而我们的交互确实叫「解锁」；`works.locked` 也确实是一个站内开关。措辞上离得很近。

**会员没有辩护空间**：`tierUnlock`（规格上限解锁）与 `healthExportUnlimited`（无限导出）都是纯站内权益，与「VIP 会员」的列举项逐字对应。

**行动**：MP 后台提工单，把五个场景的交付物形态逐条描述后问适用性。**不要自行判定后直接改** —— 若把场景 1/2/4/5 也改成虚拟支付，抽成从 0.6% 跳到 iOS 12%，而这四类是当前主要收入来源。

## 3. 改造方案

### 3.1 provider 层：加第三个实现，不改调用方

`PaymentProvider` 接口的存在让这次改造可以收敛在一个文件里。虚拟支付的语义与微信支付不同（`wx.requestVirtualPayment` 而非 `wx.requestPayment`，且有道具/代币概念），但可以映射进同一个接口：

```ts
// server/payments/virtual-provider.ts
export class VirtualPaymentProvider implements PaymentProvider {
  // create(): 返回 clientParams，端上据此调 wx.requestVirtualPayment
  //   平台按设备自动路由：安卓/鸿蒙/Windows → 微信支付，iOS → Apple 支付
  //   我们端上不做分支
  // refund(): 安卓侧可发起；iOS 侧不可发起（1.4），须抛明确错误码
}
```

**`clientParams` 要带一个 `mode` 标识**（现有代码已有 `mode: "development"` 的先例，端上据此分支）。新增 `mode: "virtual"`，端上见到就调 `wx.requestVirtualPayment`。这样三条路径（development / wechat / virtual）在端上是同一处 if-else，不散落。

**按 SKU 选 provider，不按全局环境变量选。** 这是本次改造与既有 `selectPaymentProvider()` 最大的结构差异：实体商品必须继续走普通微信支付（虚拟支付不接受实物），而会员必须走虚拟支付。所以选择依据是**订单的商品类型**：

```ts
function selectProviderForOrder(order: Order): PaymentProvider {
  if (isPhysicalSku(order.sku)) return wechatProvider;   // 实物
  if (isVirtualSku(order.sku)) return virtualProvider;    // 虚拟商品
  return wechatProvider;
}
```

`isVirtualSku` 的判定表进代码（同 `plugins/registry.ts` 的模式），**不进数据库** —— 它是合规判定的一部分，应该可版本化、可测试、可 code review。

### 3.2 端上：抬基础库到 2.19.2 的连带影响

虚拟支付需要基础库 **2.19.2+**，当前下限 **2.9.0**。抬升不是改一个数字：

- **2.9.0 这个下限是有来由的**：主题系统的 CSS 变量注入靠 `page-meta`（`theme/page-mixin.js`），而 `<navigation-bar>` 组件因需要 2.29.2 被明确否掉过（CLAUDE.md 有记录）。抬到 2.19.2 后应**重新评估** `<navigation-bar>` 之外的取舍是否变化 —— 2.19.2 仍低于 2.29.2，所以导航栏那条结论不变。
- **低版本用户的降级路径必须设计**：基础库低于 2.19.2 的用户**无法完成支付**。不能白屏或静默失败，要给「请升级微信」的明确提示。`wx.canIUse("requestVirtualPayment")` 做能力检测。
- 主题系统的四套皮肤与 `validate.js` 的十项门禁不受基础库影响（都是构建期检查），但**真机验收要在 2.19.2 与更高版本上各跑一遍**。

### 3.3 顺带修复：`growth_orders` 从未接真实支付

**这是一个独立于合规的严重缺陷，盘点时发现。**

`growth-service.ts:599` 的 `payGrowthOrder` 全文只做了三件事：查单 → `UPDATE growth_orders SET status='paid'` → 发放权益（激活会员 / 解锁年度报告 / 发健康档案凭据）。**它从不调用 `paymentProvider.create()`，也没有任何支付回调校验。**

唯一的防线是一行环境变量检查：

```ts
if (process.env.NODE_ENV === "production" && !process.env.PAYMENT_PROVIDER)
  throw new AppError("PAYMENT_ADAPTER_REQUIRED", "生产环境未配置支付供应商", 503);
```

**这行只检查「配没配」，不检查「付没付」。** 一旦生产环境设了 `PAYMENT_PROVIDER=wechat`，这个检查就通过，然后直接发会员 —— 用户调一次 `POST /api/growth-orders/[id]/pay` 就白拿 ¥128 年费会员。

对比链路 A（`orders/[id]/prepare` + `payments/wechat/notify`）是正确的：建单、预支付、等回调。**链路 B 缺的正是中间两步。**

修复要点：
- `payGrowthOrder` 改为**只在收到支付回调后**发放权益，端上流程变成 `建单 → prepare → requestVirtualPayment → 等回调`；
- 权益发放逻辑从 `payGrowthOrder` 抽出，由回调处理器调用；
- 保留幂等（现有 `if (order.status === "paid") return order` 的思路是对的，回调可能重复投递）；
- **必须补测试**。`growth-service.ts` 当前不在 `vitest.config.ts` 的覆盖率白名单里，这次要加进去 —— 它承载全部会员与权益发放。

### 3.4 iOS 退款问询接口（新增）

`xpay_subscribe_ios_refund_query_notify`，**3 秒内**响应。设计要点：

- **3 秒是硬约束**，处理器里不能有慢查询或外部调用。判定所需数据（订单状态、是否已交付、是否已消耗权益）要能一次索引命中。
- 响应 `result_code`（0 允许 / 1 拒绝）+ `evidence`（审计字段，必填）。
- **默认策略应为允许退款**，除非有明确证据表明已交付并消耗。理由：拒绝退款的下游成本（用户向 Apple 申诉、平台介入）远高于退一单;而三次不响应会把决定权完全交给 Apple，等于既得不到退款也留不下审计记录。
- 落审计日志（复用 `operation_audit_logs` 或新表），退款争议要能追溯。

### 3.5 定价的连带调整

- **iOS 单笔最低 1 元**。当前无低于 1 元的 SKU，暂不受影响，但**未来不能出现 ¥0.9 档**。
- **免费玩法（`unlockPrice: 0`）不受影响** —— 不产生订单，不走支付。
- 抽成从 0.6% 涨到 1%（安卓限时）/ 12%（iOS）后，**毛利需重算**。`domain/pricing.ts` 的三档定价是按旧费率定的，改造后应复核 —— 尤其 ¥12.9 的海报在 iOS 上要交 ¥1.55。

## 4. 风险与未决项

### 4.1 上线级阻塞

| # | 阻塞 | 说明 |
| --- | --- | --- |
| 1 | **主体资质** | 须已认证的企业/事业单位/个体工商户。若当前是个人号，**整条路走不通**，需先变更主体 |
| 2 | **场景适用性判定**（2.3） | 决定改造范围是「只改会员」还是「五个场景全改」，两者工作量差数倍 |
| 3 | **开通周期** | 审核 1–7 工作日 + 签约 1–2 工作日 + iOS 简称审核，串行不可压缩 |

### 4.2 待拍板项

| # | 待定 | 建议 |
| --- | --- | --- |
| 1 | 是否引入代币 | **不引入**。名称与比例不可修改，且代币是「充值-消耗」模型，与我们「一次性买交付物」的形态不匹配 |
| 2 | 低基础库用户 | 明确提示升级微信，不静默失败 |
| 3 | iOS 用户占比 | 需先取数。若 iOS 占比高，12% 抽成对毛利的影响需重新评估定价 |
| 4 | 会员是否改为订阅制 | 虚拟支付的「会员订阅」费率是首笔 1%、第二笔起 10%，与「主动支付」不同。当前会员是一次性购买 |
| 5 | 是否借机重构 provider 选择 | 建议按 SKU 选（3.1），而非扩展环境变量 |
| 6 | E2E 如何覆盖 | iOS 无沙箱（1.4）。建议 E2E 只覆盖安卓沙箱路径 + development provider，iOS 走人工验收清单 |

### 4.3 与「宠物小岛」的关系

`22` 号文原先的结论是「装饰不卖，让虚拟支付整个不存在」。该结论需修正：**装饰可以卖，前置条件是本文的改造完成。** 但仍**不建议**为装饰单独做商店：

- 装饰客单价低，而 iOS 抽成 12%；
- 更划算的做法是**把装饰并入会员权益**（会员本来就要接虚拟支付），一次接入覆盖两个场景。

见 `22` 号文 1.2 与 7 章的修订。
