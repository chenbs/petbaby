## 1. 严重 · 立绘被打两次 AI 标识，第一个变成半透明脏块

**位置**：`server/growth-service.ts` 的 `processNextAiRun`（原第 146 行无条件打标）
配合 `server/island/avatar.ts` 的 `adoptAvatarCandidate`（原第 272–273 行抠图 + 再打标）

### 现象

用户的立绘右下方悬着一块**半透明深色残影**，下面才是真正的「AI 生成」标识。
而立绘是要**实时叠在浅色草地上**渲染的，脏块会直接透出来。

### 链路

`processNextAiRun` 对**所有** `ai_runs` 无条件 `applyAiLabel`，不区分 `plugin_id`。
而 `adoptAvatarCandidate` 从 `candidate.outputKey` 取字节 —— 那份**已经被打过标**。于是：

```
打标(深绿黑底衬) → 抠图 → 再打标(岛专用底衬)
```

### 为什么不报错（这是关键）

逐像素实测（用真品红底 + 主体圆的合成图，复现两个函数的实际输出）：

- 第一个标识落在 1024px 图的 `x:904 y:964`，即**画面右下角、品红背景区内**；
- 抠图把它当前景处理：深绿黑底衬 `#14251c` 的 `min(R,B)-G` 正好落进羽化带
  （30 ≤ level ≤ 110），该区域 **4000 像素里 3658 个变成半透明**（alpha 16–240），
  底衬色还被去溢色改写；
- 缩放到 1200×1600 后残影落在 **y≈1330–1377**，而第二个标识画在 **y≈1504–1568** ——
  **两块不重叠**，所以不是「标识画重了」而是多出一块鬼影。

而 `cutoutSprite` 的所有判据都通过：`clearedPercent` 实测 **72.64%**（远超 25% 门槛）、
`keyed: true`；残留统计只算 `level > RESIDUE_VISIBLE_LEVEL` 的**前景**像素，
而残影落在羽化带里、根本不进 `residue` 计数。**返回值一切正常。**

### 修法

**抠图与打标都挪到生成时（`processNextAiRun`），选定时只另存字节。**

```
抠图 → 打标一次（岛专用底衬）   # processNextAiRun
另存到岛的键                      # adoptAvatarCandidate
```

不是简单地「让岛跳过第一次打标」—— 那样候选预览会变成没有标识的品红底方图，
而**预览必须从已打标字节缩**（既有约定，否则免费预览没标识、付费版有，正好搞反），
且四选一页给用户看的应当就是入岛后的样子。

`keyed` / `residuePercent` 随候选存进 `ai_runs.candidates`，`adopt` 从那里读 ——
为拿一个数字把图再抠一遍是白花的 CPU，且算两遍多一处会漂移的地方。

### 顺带修掉的第二个缺陷

改完后 25 个测试挂了，暴露出一个**既有的、更隐蔽的**问题：
`processNextAiRun` 的预览水印 SVG 写死 `640×640`，而 `fit: "inside"` 只保证长边 640 ——
立绘是 3:4（1200×1600），缩完是 **480×640**，往上叠一张 640×640 会被 sharp 判为
「composite 输入大于画布」并**直接抛错**，整个任务 failed（错误码
`Image to composite must have same dimensions or smaller`）。

既有 provider 恰好都返回正方形图，所以这个坑一直没被踩到。已改为按缩放后的真实尺寸生成水印。

### 门禁

`island/avatar.test.ts` 新增「抠图在打标之前：立绘上只有一个标识，没有半透明残影」：
用**真品红底**输入（不是本地 provider 的橙色 SVG —— 那会走原样透传的降级分支，
残影根本不出现，测不到这个缺陷），逐像素断言残影区不透明像素为 **0**、标识区 **>500**。

实测可拦：把顺序改回「先打标再抠图」，该用例报 `expected 5633 to be +0`。
修复前后对比：残影区不透明像素 **5633 → 0**，真标识不变（891）。

## 2. 严重 · `/api/island` 忽略端上传的 `petId`

**位置**：`app/api/island/route.ts`（原只读 `candidates` 参数）、
`server/island-service.ts` 的 `getIslandSnapshot` / `loadIslandPet`

### 现象

宠物档案里有两只，点第二只的「小岛」按钮，进去看到的是**第一只**的名字、天数和立绘。

### 为什么不报错

端上做对了：`pages/pets/pets.js:84` 带上了 `petId`，`island/service.js:25` 拼成 `?petId=`。
但服务端 `GET /api/island` 只认 `candidates`，`getIslandSnapshot` 连这个形参都没有，
`loadIslandPet` 一律 `ORDER BY ip.joined_at LIMIT 1`。**参数被静默丢弃**，
Next 不校验未使用的 query，快照本身合法、字段齐全，只是那只宠物不对。

CLAUDE.md 把「入口必须带 `petId`，不带的话点非默认宠物会看到错的那只」列为硬约束 ——
端上那一半做了，服务端那一半没有。

M1 阶段 `MAX_ISLAND_PETS = 1`，只有一只宠物入过岛的用户完全看不出问题，
**这是它至今没暴露的原因**；M2 放开多只入岛后会立刻变成必现缺陷。

### 修法

`getIslandSnapshot` 接 `petId` 并传给 `loadIslandPet`，SQL 里用
`ORDER BY (ip.pet_id = $2) DESC, ip.joined_at`。

**是优先项而不是过滤条件**：用 `WHERE pet_id = $2` 的话，传进来的宠物没入岛时
快照会变成「岛上没有宠物」，而用户明明看得到岛上住着一只。排序优先则是
「有就给你要的那只，没有就给岛上那只」。

### 门禁

`island-service.test.ts` 新增「快照按端上传来的 petId 给对应那只」：
**绕过 `MAX_ISLAND_PETS` 直接写第二行 `island_pets`** —— M1 走 `joinIslandPet`
拿不到「岛上有两只」的状态，而那是唯一能区分「读了 petId」与「没读」的情形。
三个分支都验：不传给最早入岛的、传第二只给第二只、传没入岛的回落到岛上那只。

E2E 另加一条守路由层（原缺陷正在那一层）。实测可拦：去掉参数传递后报
`expected f3 to be f5`。

## 3. 严重 · 立绘缓存键不带内容哈希，换形象后画面永远是旧的

**位置**：`apps/miniprogram/island/scene/assets.js` 的 `loadImage`（内存层）与
`fetchToLocal`（磁盘层）

### 现象

在 `island/avatar` 页重画形象、选定、返回岛，快照里 `avatarUrl` 已经是新地址了，
但画面上**还是上一版立绘**。杀掉小程序重进也一样（`saveFile` 是持久缓存）。
唯一能解开的是系统清缓存，或 8MB 预算把它淘汰掉。

### 为什么不报错

两层缓存都**只认 `key`、完全不看 `url`**：
`loadImage` 首行 `if (decoded[key]) return ...`，`fetchToLocal` 同样只按 `key` 查索引。

场景素材这样做是对的 —— 键名带内容哈希，换图必须换键，所以缓存永不失效。
但立绘的键是端上**硬编码的常量** `"pet-avatar"`，而它对应的 URL 会变：
`adoptAvatarCandidate` 写的键是 `private/<uid>/island/avatar-<petId>-<runId>.png`,
**每次重新生成 `runId` 都不同**。

缓存命中是正常路径，没有任何一层会去比对「这个键当初是从哪个 URL 下的」。

### 修法

两层都存 url 并在命中时比对：磁盘层记进索引条目（`{ path, size, usedAt, url }`），
内存层记在图片对象上（`image.__url`）。不一致就当未命中，重下并真删旧条目。

**不把 url 并进键名**：那样 `renderer.js` 就取不到固定的 `pet-avatar` 了，
而渲染器正是按逻辑键找图的。老缓存条目没有 `url` 字段，按「对不上」处理重下一次。

### 门禁

`scripts/island-renderer.test.js` 新增「同一个键换了 url 时重新下载」：
同键同址命中不重下、同键换址必须重下且拿到新文件、旧条目被真删。
实测可拦：去掉 url 比对后报「换了地址却仍命中旧缓存 —— 用户会一直看到上一版立绘」。

## 4. 中 · 岛的立绘任务能被通用 `/api/ai-runs/*` 操作

**位置**：`server/growth-service.ts` 的 `selectAiCandidate` / `rerollAiRun` /
`retryAiRun` / `cancelAiRun`

### 现象

用户或脚本拿 runId 打 `PATCH /api/ai-runs/<id>` 带 `candidateId`，会建出一条
`plugin_id='island-avatar'` 的 `works` 行。而 `island-avatar` **刻意不在 `registry.ts` 注册**，
于是 `hydrateWork` 的 `getRuntimePlugin("island-avatar")` 返回 undefined → 抛 `WORK_INCOMPLETE`。

**那一行打不开也删不掉，而 `listWorks` 对每一行都 `hydrateWork` —— 一条脏行让整个作品列表 500。**

已实测确认：select 静默成功、`works` 多出一行、`listWorks` 抛「作品关联数据不完整」。
这正是 CLAUDE.md 里「archived manifest 不能删」要防的故障模式，只是从另一头进来的。

`rerollAiRun` 同理：它会清 `candidates` 并删除对象字节。`island_pets.avatar_key` 指向
另存的键所以立绘不裂，但用户白掉一次立绘额度、岛内候选凭空消失，两处都不报错。

### 为什么不报错

岛自己的三条路由都带了 `AND plugin_id=$3`，而通用路由**只按 `id + user_id` 查**，
没有对称防护。

### 修法

**拦在服务层而不是路由层** —— 通用侧有五个入口，逐个路由加必漏改一处。
`selectAiCandidate` / `rerollAiRun` 走 `assertNotIslandRun()`（它们本来就读 `pluginId`）；
`retryAiRun` / `cancelAiRun` 在 SQL 加 `AND plugin_id<>$3`（它们不读 `pluginId`，
多查一次只为拿一个用来拒绝的值不值得）。

只读的候选预览路由不拦：它只返回用户自己的预览字节，无副作用。

### 门禁

`island/avatar.test.ts` 新增「通用 ai-runs 接口拒绝岛的立绘任务，作品列表不被污染」：
四个入口逐个验错误码、断言 `works` 零行、`listWorks` 仍可打开、候选还在（reroll 被拦住）。
实测可拦：去掉 select 的守卫后该用例失败。

## 5. 中 · 素材漏灌校验的两个「消费方」都不存在

**位置**：`server/island/assets.ts` 的 `configuredIslandAssetCount()`

### 现象

该函数注释写着「`/api/health` 与冒烟脚本用它判断有没有漏灌」，但搜遍 `src/` 与
`deploy/scripts/` —— **零调用方**。`/api/health` 与 `config.ts` 里没有 `island` 字样，
`smoke-test.sh` 也没有。

CLAUDE.md 明确记着这个故障模式：「漏灌时 `/api/plugins` 与 `/api/health` 均正常，
只有 `<image>` 取字节时 404，端上表现为大面积裂图且不报错」。岛的素材走同一条
`samples/` 前缀，却没有对应校验。

### 修法

- `healthSnapshot()` 增加 `islandAssets`（张数）与 `islandAssetPaths`（站内相对路径清单）。
  **不参与 `status` 判定** —— 素材清单为空是正式状态，算进健康与否会把正常状态报成 degraded。
- `smoke-test.sh` 增加一段：读 `/api/health` 拿张数与路径，逐张取字节。

**清单从 `/api/health` 读而不是 `/api/island`**：后者要鉴权（`requireUserId`），
而冒烟脚本在 Compose 网络内无会话地直连 web —— 读它只会拿到 401，
于是「取不到地址」被当成「没配素材」**静默通过**，那正是这个校验要防的事。

**清单为空不算失败**：素材未回填时端上走「素材未就绪」路径，功能可用。
只在「配了但取不到」时报错。

### 门禁

`island-service.test.ts` 新增「健康快照报告岛素材张数与路径，两者同源」：
张数与清单长度一致、空清单时 `status` 仍为 `ok`、路径是站内相对路径。
E2E 另验 `/api/health` 实际输出这两个字段。

## 6. 中 · 部署脚本不灌岛素材，且工具打印的粘贴目标是错的文件

**位置**：`deploy/scripts/seed-samples.sh`、`tools/imagegen/upload-island.mjs`

### 现象两个

**其一，粘贴目标是错的。** `upload-island.mjs` 打印「把下面这段并入
`apps/platform/src/plugins/island/assets.ts`」、变量名 `ISLAND_ASSETS` ——
而真实文件是 `apps/platform/src/server/island/assets.ts`、变量名 `ISLAND_ASSET_PATHS`。
照打印的做会**新建一个没有任何读取方的文件**：`islandAssetUrls()` 仍从原处读空清单，
端上继续走「素材未就绪」路径，而人以为素材已经接上了。

**其二，素材到不了部署机。** `seed-samples.sh` 只扫 `out/plugins` 与 `out/styles`，
且一律按 `.jpg` 命名、写死 `image/jpeg`。而岛素材：

- 键落在 `samples/island/` 前缀下，脚本不认；
- 需要 alpha 的槽位输出 **PNG**，写死 jpg 会让 contentType 与实际字节不符；
- 必须先**抠品红底、按槽位裁切**，而那两步只有 `upload-island.mjs` 会做 ——
  `out/island/` 里躺的是人工投放的原图（品红底、尺寸未裁），
  直接灌进去等于给端上一张带品红背景、比例不对的图。

素材到齐后走 `release.sh` 部署，岛素材不会进卷。**表现正是「接口全正常、只有取字节 404、
端上大面积裂图且不报错」。**

### 修法

- `upload-island.mjs` 修正打印的路径与变量名。
- 新增 `--stage <目录>`：额外输出一份**按最终对象键布局**的副本
  （`samples/island/<名字>-<哈希>.<ext>` + `.meta` 旁文件）。
- `seed-samples.sh` 读那个 staged 目录整目录并入暂存区。缺它时**只 warn 不失败**
  并打印该跑的命令 —— 清单为空是正式状态。

**不读 `--keep` 写的 `keyed/`**：那里只有需要 alpha 的那几张（没有场景底图与入口卡图），
且被 `.gitignore` 排除，到不了部署机。

顺带修掉：抽查那行 `ls | head -1` 现在可能挑中新增的 `island/` 子目录，
改成 `find -maxdepth 1 -type f`。

### 验证

用现有的 `pet-sample.png` 实跑 `--dry-run --stage`：产出
`samples/island/pet-sample-<哈希>.png` + `.meta`（`{"contentType":"image/png"}`），
且 dry-run 未污染本机 `.data/objects`。再模拟 `seed-samples.sh` 的拷贝段，
确认岛素材正确嵌到 `samples/island/`、抽查那行挑中的是 `.jpg` 而不是目录。

## 8. 过程中的两处环境问题（不是代码缺陷，但值得记）

**PGlite 测试库会被中断的并发跑坏。** 全量 vitest 一度 118 个用例失败，报
`could not read blocks 0..0 in file "base/5/..."` —— 是我中断的并发测试跑损坏了
`apps/platform/.data/petbaby`。那是 gitignored 的本地缓存，`rm -rf` 后按迁移自动重建，
643 个用例全绿。**遇到大批莫名失败且错误来自 pg-protocol 时，先怀疑这个而不是代码。**

**`ai/provider.ts` 当时正被另一处改动（PACKY→LINGSUAN 重命名）占用。**
它的类型错误会级联到 `growth-service.ts`（`generateWithFailover` 的返回类型是推断的，
文件坏了就塌成 `any`），一度看起来像我的改动引入了错误。用 HEAD 版本对照排除后确认无关，
并原样还原了那个文件 —— **未做任何改动**。
