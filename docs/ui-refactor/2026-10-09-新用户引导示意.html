A · 无宠物时的首页（唯一新画面）

优点

  • 改动最小：只换首页第一块与玩法点击守卫，复用现有 pets 建档弹层和见面礼弹窗。
  • 不打断浏览：先逛后建档的用户不受阻拦，分享卡进来的人能马上看到样片。
  • 建档从两跳变一跳，并把见面礼前置成建档理由。
  • 无宠物与有宠物共用一份首页 DOM，四套主题只需补一个空态卡样式。

缺点

  • 建档仍是可选项，用户可能一直往下刷，到点样片时才被弹层拦住。
  • 「建档后可用」角标多了显得像锁门，和精致基调有冲突，需要控制出现次数。
  • 建档只填名字和物种，不带照片，名片点亮后仍是首字母头像，第一印象偏空。
方案 B首次进入的三步轻引导

首次打开且无宠物时铺满一个三步引导：选物种 → 名字 + 一张照片 → 完成并领见面礼，回到首页时名片、陪伴天数、照顾条一次点亮。首页本身只保留现有的小卡作为跳过后的兜底。

跳过引导时的兜底：沿用现有小卡，按钮改为直达建档
B0 · 跳过后的首页（基本不变）

优点

  • 建档率高：一进来就在做一件事，三步走完名片、陪伴天数、照顾条一次点亮。
  • 顺手拿到第一张照片，头像和后续玩法的身份照都有了，首屏不再是首字母头像。
  • 完成页直接把见面礼接到一款玩法，建档到首次消费的路径最短。
  • 首页几乎不改，有宠物用户零影响。

缺点

  • 挡在内容前面：从分享卡或样片进来、只想看一眼的人会被拦，跳出率可能上升。
  • 新增一个引导页面 / 分包，要处理「只出现一次」、跳过、登录态失效、上传失败等状态。
  • 引导里传照片需要复用照片页的上传会话与幂等回执，不能另写一套，开发量明显大于 A。
  • 微信审核对首次强制流程较敏感，「先逛逛」必须常驻且不能弱化。
