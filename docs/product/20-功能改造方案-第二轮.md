## 第一部分：最严重的问题——会员权益无法兑付

### 1.1 事实

17 号文 3.6 设计的 ¥128 年度会员，四项核心权益中**三项没有任何兑付代码，第四项的实现方向是反的**。

**【代码事实】** `src/server/entitlements.ts` 全文 49 行，只导出两个函数：

| 权益（迁移 0020 写入 `membership_plan_versions.entitlements`） | 单买标价 | 兑付实现 |
| --- | --- | --- |
| `tierUnlock` 交付物规格上限解锁 | ¥49 | 有 `hasTierUnlock()`，**但方向是反的**（见 1.2） |
| `healthExportUnlimited` 健康档案 PDF 无限导出 | ¥29.9 | 有 `hasHealthExport()`，**零调用方** |
| `annualHealthReport` 年度健康报告 ×1 | ¥39.9 | **只有 TypeScript 接口字段，无函数、无调用方** |
| `annualReport` 年度报告（创意）×1 | ¥19.9 | **只有接口字段，无函数、无调用方** |
| `physicalDiscount` 实体 9 折 | — | **只有接口字段。** `createPhysicalOrder`（`growth-service.ts:386`）直接 `const amount=Number(sku.amount)`，不查会员 |

`grep -rn "hasHealthExport\|annualHealthReport\|annualReport\|physicalDiscount" src/` 的非测试结果只有 `entitlements.ts` 自身的 5 行声明。

**五项权益无一项可兑付**：四项完全没有兑付代码，第五项（`tierUnlock`）有代码但方向是反的（见 1.2）。

按标价算，¥128 会员里 ¥89.8（70%）是明确不存在的功能，其中 ¥69.8 依赖 A5 健康档案 PDF 与 A6 年度健康报告——这两项 17 号文第五部分之二自己标了「⏸ 未实施」。剩下 ¥49 的 `tierUnlock` 不是「不存在」而是「反向计费」，性质更严重。

**这意味着会员是可售且可支付的**：`createMembership` 查 `status='active'` 的套餐版本，迁移 0020 已把 v2 ¥128 置为 active。用户能付钱，付完拿不到东西。

### 1.2 `tierUnlock` 的实现让会员倒亏

**【代码事实】** `src/server/platform-service.ts:413`：

```
const tier = accumulation
  ? ((await hasTierUnlock(userId)) ? MEMBER_TIER : resolvePriceTier(accumulation))
  : undefined;
const amount = (tier && tierPrice(work.pluginId, tier)) ?? base;
```

`MEMBER_TIER`（`domain/pricing.ts:70`）等于 `"annual"`，即**最高档**。而 `TIER_PRICES` 里画册的 annual 档是 ¥49、basic 档是 ¥19.9。

于是：**一个只有 10 张照片的会员，买画册的价格是 ¥49；同样 10 张照片的免费用户，价格是 ¥19.9。会员多付 ¥29.1。**

「规格上限解锁」被实现成了「按最高档计价」。设计意图是「不看照片数也能做最好的规格」，落地成了「不看照片数都收最高价」。`domain/pricing.ts:69` 的注释写的是「直接给最高档，不看照片数」——注释与意图一致，但「给最高档」在计价函数里的唯一含义就是「取最高档的价」。

**这是本文发现的最严重缺陷。** 它不会被任何测试捕获：`pricing.test.ts` 测的是档位解析函数本身，`entitlements.test.ts` 测的是权益读取，两者都正确；错在**组合语义**。

### 1.3 两端在卖已下线的套餐

**【代码事实】** 迁移 0020 已执行 `UPDATE membership_plan_versions SET status='inactive' WHERE code='monthly'`，且年度会员改为 v2 ¥128。但：

- `src/components/commerce-client.tsx`：按钮文案写死 `月会员 ¥25` / `年会员 ¥199`。点月会员会命中 `MEMBERSHIP_PLAN_UNAVAILABLE`（409）；点年会员实际扣 ¥128 而界面承诺 ¥199。
- `apps/miniprogram/pages/commerce/commerce.js:6-19`：`PLANS` 数组同样是月 ¥25 / 年 ¥199，且权益文案写着「**每月生成额度加量**」「**额度按月自动重置**」——正是 17 号文 D6 明确要删除的负向卖点（比免费额度还少）。

**标价 ¥199、实收 ¥128 是价格欺诈风险**，方向虽是少收，但承诺与履约不一致同样构成投诉与退款理由。而「额度加量」在新权益下根本不存在（迁移 0020 的注释自己写明「会员不卖次数」）。

### 1.4 年报解锁不查会员

**【代码事实】** `growth-service.ts:498` `createAnnualReportUnlockOrder` 硬编码 `amount=19.9`，全函数无任何会员判定。

付了 ¥128（权益含「年度报告 ×1」）的会员，解锁年度报告仍要另付 ¥19.9。

### 1.5 改造要求

| # | 项 | 要求 |
| --- | --- | --- |
| **M1** | `tierUnlock` 语义修正 | 会员的档位解锁必须表现为**免费或折扣**，不能是「按最高档计价」。建议：会员按实际积累量定档，但**价格取 basic 档**（即「用最高规格、付最低价」）；或直接把会员的交付物解锁价设为 0 并计入权益额度 |
| **M2** | 停售无法兑付的权益 | A5/A6 未实施期间，`membership_plan_versions` 的权益 JSON 必须移除 `healthExportUnlimited` / `annualHealthReport`；`annualReport` 与 `physicalDiscount` 保留但**必须同时补上兑付代码**（M4 与实体折扣），否则一并移除。价格从 ¥128 下调至与实际可兑付权益相称的水平——`tierUnlock`（修正后）+ 年报 ¥19.9 + 实体 9 折，约 ¥69 |
| **M3** | 两端价格与权益文案同源 | Web 与小程序的套餐名、价格、权益列表一律从 `/api/memberships` 的套餐版本读取，禁止端上写死。当前三处（迁移、Web、小程序）各一份必然走散 |
| **M4** | 年报解锁接入会员判定 | `createAnnualReportUnlockOrder` 检查 `annualReport` 权益余量，命中则直接置 `locked=false` 并记 `entitlement_ledger`，不建订单 |
| **M5** | 权益兑付的测试口径 | 每项权益必须有一条「会员用户走完整链路拿到该权益」的用例。当前 346 个用例全绿却漏掉全部兑付路径，说明测试覆盖的是函数而非权益 |

**M1/M2 是上线阻塞。** 会员是唯一的订阅收入，且它当前的状态是「收钱、少给、部分不给」。

## 第二部分：情绪价值评估

用户提出「情绪价值不够」。**核实结论：判断成立，但原因与直觉相反——不是内容不够动人，而是产品从不主动出现。**

### 2.1 已建成的情绪价值资产（做得比多数竞品好）

**【代码事实】** 这几项的实现质量高于 16 号文对标的任何竞品：

| 资产 | 落点 | 为什么算好 |
| --- | --- | --- |
| 陪伴天数封口 | `domain/companion.ts` + `services/companion.js` | 纪念页按 `memorialSince` 截止、年度视频按年末封口。**天数不跟着今天涨**——这是极少有产品会想到的克制 |
| 两套时间口径 | `photos.shot_at` vs `created_at` | 「第 N 天」按拍摄时间、「今年收藏了 N 张」按行为时间。混用会把今年上传的旧照片算进往年 |
| 去年今日只认真实拍摄时间 | `timeline-service.ts:141` | 上传时间的月日撞上今天纯属巧合，硬凑出来的「回忆」是产品的表演 |
| 里程碑不含第 1 天 | `MILESTONE_DAYS` | 起点不是成就 |
| 纪念线零打扰 | `memorial-service.ts` | 无弹窗、无推销、无热度榜 |
| 健康线 memorial 屏蔽 | `health-service.ts:98` 服务端 + 端上双拦 | 已离开的宠物收到体检提醒是不可接受的 |

**这些不是小事。** 一个愿意为「天数不该继续涨」写三处封口逻辑的产品，情绪判断力是在线的。

### 2.2 但情绪价值全部是「被动等待」

**【代码事实】** 逐条核实主动触达链路：

| 情绪触点 | 服务端 | 端上入口 | 主动触达 |
| --- | --- | --- | --- |
| 成长时间线 | ✅ `getPetTimeline` | 小程序**仅** `pets` 卡片可进；**Web 无此页** | 无 |
| 去年今日 | ✅ `findOnThisDay` | **仅 Web 首页区块**；小程序无 | 见 2.3 |
| 里程碑 | ✅ `milestones` 已算出并随时间线下发 | **无任何端上渲染** | 无 |
| 陪伴天数 | ✅ | 小程序 `me` / `pets` / `memorials` / `timeline` 四页；**首页无** | 无 |
| 年度报告 | ✅ | `commerce` 页（「会员与年度报告」）二级入口 | 无 |
| 叙事年度视频 | ✅ `POST /api/annual-films` | **零端上调用方**（`grep` 全仓无结果） | 无 |
| 月度小册（A9） | ❌ 未实施 | — | — |
| 里程碑自动产出（A8） | ❌ 未实施 | — | — |

**【代码事实】** `scripts/worker.ts` 每 60 秒的运维轮次里，唯一与情绪相关的是 `scheduleAllUpcomingReminders`（生日提前 7 天）与按小时的 `scheduleAllOnThisDay`。除此之外**没有任何主动触达**。

**【推断】** 这解释了「情绪价值不够」的真实来源：**所有动人的东西都要用户自己想起来去翻。** 而用户不会想起来——他们打开小程序的动机是「做张图」，首页给的也正是玩法货架（`pages/index/index.wxml` 全文 **0 处**出现宠物或陪伴字样，**【代码事实】**）。

情绪价值不是内容问题，是**分发问题**。时间线写得再好，一个只能从「我的 → 宠物档案 → 点某只宠物」三层进入的页面，触达率接近于零。

### 2.3 去年今日的推送链路有授权缺陷

**【代码事实】** `timeline-service.ts:173` `scheduleOnThisDay` 直接 `INSERT INTO message_subscriptions (... status='scheduled')`——**它凭空创建订阅记录，从不检查用户是否授权过**。

对比 `growth-service.ts:354` 的 `subscribeReminder`：它要求 `consent: z.literal(true)` 且按 `wechatAuthorization` 决定 `status` 是 `active` 还是 `authorization_required`。

而 `messaging/worker.ts` 的 `processDueMessages` 取的是 `status IN ('active','scheduled')`——**去年今日写入的 `'scheduled'` 会被直接投递**。

微信订阅消息是「一次授权一次下发」，无授权下发会被平台拦截并可能影响小程序信誉。**这是合规与技术双重问题，且它恰好在唯一已接通的主动触达路径上。**

### 2.4 情绪价值的改造要求

| # | 项 | 要求 | 理由 |
| --- | --- | --- | --- |
| **E1** | 首页第一屏改为宠物 | 小程序 `index` 首屏给默认宠物的封面 + 陪伴天数 + 去年今日（命中才显示），玩法下移 | 17 号文把这条排进批次 4「需外部条件」，但它不需要任何外部条件，只需要重排。**且它是情绪价值触达率从 0 到 1 的唯一开关** |
| **E2** | 去年今日补授权门 | 命中后先检查该用户是否有 `on_this_day` 的有效授权；无授权则只在端上静默展示、不写投递记录 | 2.3 的合规缺陷 |
| **E3** | 里程碑渲染 | 时间线已下发 `milestones`，端上补渲染；达成当天在首页出现一次 | 零服务端成本，数据已在 |
| **E4** | 小程序补去年今日 | 与 Web 首页同一区块 | 小程序是主端，Web 有而小程序没有是反的 |
| **E5** | `annual-films` 补入口 | 挂在 `commerce` 的年度报告旁或 `timeline` 页尾 | 已建成的能力零触达是纯浪费 |
| **E6** | Web 补时间线页 | 与小程序 `pages/timeline` 同数据源 | 积累层的底座只有单端 |

**E1 是本轮情绪价值改造的唯一支点。** 其余五项都是「补入口」，只有 E1 改变的是「用户打开时先看到谁」。

### 3.2 L4 需要单独说明：`senior` 是一个空标签

17 号文 3.3 把「生命阶段三态」列为 C4/C9 的前提，并明确 `senior` 的产品行为是「健康提醒加密；画册/短片调性转克制；纪念线入口出现但不推送」。

**【代码事实】** 三条的实现状态：

1. 健康提醒加密——不存在任何健康提醒（L5），无从加密
2. 调性转克制——`registry.ts` 的三个 `toneVariants` 只有 `memorial` 键，无 `senior`
3. 纪念线入口出现——`memorials` 页的入口在 `me` 页固定展示，与生命阶段无关

**所以 C9「纪念可达性」的验收结论（17 号文标 ✅，理由是「由 C4 的 toneVariants 承载」）只对 `memorial` 成立，对 `senior` 不成立。** 而 `senior` 恰恰是 16 号文 P1-3 认定「付费意愿峰值」的那一段。

**【推断】** 当前 `senior` 的唯一效果是：用户手动设成晚年后，什么都不会变。这比没有这个选项更差——它给了一个承诺然后什么都不做。

## 第四部分：哪些功能可以合并

17 号文已把 10 个 manifest 合并到 7 live，方向正确。**剩余的合并空间不在 manifest 层，在页面层。**

### 4.1 页面层的重复

**【代码事实】** 小程序 24 页中，以下几组是同一件事的多个入口：

| 组 | 页面 | 重复点 | 建议 |
| --- | --- | --- | --- |
| **A** | `growth`（选择创作方式）+ `index`（玩法列表） | `growth` 的全部内容是 `/api/plugins` 的子集筛选。**它存在的唯一理由是首页曾经放不下** | **删 `growth`**，其三类玩法（AI/互动/视频）已在首页按 category 分流，`me` 的「AI、互动与视频」入口直接指首页 |
| **B** | `commerce`（会员+年报+实体入口）+ `physical`（实体下单） | `commerce` 承载了三件无关的事：订阅、年度报告、实体商品跳转 | 拆而非合：会员权益独立成页，年度报告归入作品线，实体归入作品的「做成实物」动作 |
| **C** | `memorials`（纪念空间）+ 画册/短片的 memorial 调性 | C4 已把纪念**产物**合并，但纪念**空间**仍是独立页 | 保留 `memorials`（它是空间不是玩法），但入口改为挂在 `senior`/`memorial` 宠物上（L4） |

### 6.2 付费结构的三个判断

**判断一：单次交付物的结构是对的，但价格锚仍然缺失。**

分档定价（¥19.9 → ¥49）让画册有了 2.5 倍的价格跨度，这是 16 号文 P2-3「七个价格挤在三倍区间、没有价格锚」的正确解法。**但用户看不到这个跨度**（L3），所以锚不成立——锚的作用是让用户理解「贵的贵在哪」，看不见的锚等于没有。

**修 L3 的收益可能大于加任何新功能。** 让用户在制作前看到「你的 45 张照片可以做进阶画册 ¥39.9，再攒到跨度满一年可做年度画册 ¥49」，这句话同时完成三件事：解释价差、给出攒的动力、避免诱导风险。

**判断二：会员是唯一的订阅收入，而它现在不能卖。**

M1/M2 修好之前，¥128 会员应当**下架**。理由不是保守：它当前的状态是收钱后少给（`tierUnlock` 反向）加不给（三项无兑付），这在支付纠纷里没有辩解空间。

**降级方案**：把会员权益收敛到已实现的部分，定价随之下调。可兑付的只有 `tierUnlock`（修正语义后）与 `annualReport`，单买约 ¥69，会员定价 ¥59–69 是诚实的。等 A5/A6 上线再回到 ¥128。

**判断三：健康线的付费点设计正确，但先决条件未满足。**

「分诊免费、病历付费」的逻辑自洽（收费即暗示对结论负责，与免责声明矛盾）。但健康线目前：

- 无主动触达（L5）→ 不构成日常打开理由 → 用不到病历
- 无健康交付物（L1/L2）→ 无付费点
- 体重只存不算（L6）→ 病历里最有价值的曲线没有解读

**【推断】** 健康线现在的实际状态是「一个做得很合规的单次问答工具」。它的合规实现（关键词直通、药物后置过滤、13 条对抗测试）质量很高，**但合规不产生留存**。让健康线成为高频场景的是 L5 的主动提示，不是分诊本身——用户不会每天想起来问一次「我的猫怎么了」。

### 11.2 四处偏离与补充

**一、M1 的「省多少」不能直接宣称（正文 9.1 方案 A 未涉及）。**

方案 A 说「用户能一眼算清省了多少」。实现时发现按**只做一件交付物**的保守口径，¥69 会员的权益只值 ¥49（一次档差 29.1 + 年报 19.9）—— 低于定价。此时宣称「省 ¥N」是假的。

处理：`domain/membership.ts` 的 `saving` 只在真为正时给值，否则给 `breakEvenDeliverables`（做几件回本，¥69 是 2 件）。tierUnlock 的价值随件数线性增长，「两件回本」是用户能自己验证的事实，而「省 ¥20」不是。

**二、E2 的授权门必须同时消耗授权（正文 2.3 只要求「补授权门」）。**

正文的要求是「命中后先检查是否有有效授权；无授权则只在端上静默展示」。只做这一半仍不合规：微信订阅消息是**一次授权一次下发**，拿一条 active 授权反复推送同样会被拦截 —— 那只是把「从不授权」换成「授权一次、推送无限次」。

实现里排期与消耗成对发生（授权行置 `status='consumed'`），并且 `subscribeReminder` 必须放行 `on_this_day` 这个 eventType —— 否则补了门之后该推送**永远无法被授权**，功能静默失效。两处必须同时改。附带需要迁移 0021 给 `message_subscriptions` 加 `status_updated_at` 列（memberships 早有同名列，这张表一直没有，那条 UPDATE 会在运行时报错，而它只在 Worker 轮次里跑，本地不起 Worker 时不暴露）。

**三、正文 5.2 与 6.1 漏了三处同类缺陷。**

「Web 实体 SKU 硬编码」（正文已记）只是这一类的一例，实际还有：

- **Web 作品页无解锁入口且无任何价格文案**。正文 L3 只说「档位不可见」，实际是连解锁按钮都没有 —— 从作品柜进来的用户唯一出路是回制作页重做。
- **小程序作品页的价格从未显示过**。`work.js` 读 `work.unlockPrice`，而 `PublicWork` 上没有这个字段（价格在 `work.plugin.pricing.unlockPrice`），所以按钮一直走兜底文案「解锁高清无水印」。正文 6.1 把 PL-03/PL-19 记作「✅ 通，但档位下单前不可见」，实际是**两端都从未显示过任何金额**。
- **`create-flow.tsx` 仍在拼已下线的 `pet-id-card-bundle`**，走到该分支必然 422。

**四、正文 附录局限 5 提到的后台路径确实有缺陷（该局限说「未核实」）。**

核实结果：`/api/admin/business` 的 `create_plan` 把 `{ monthlyQuota }` 当**整个**权益 JSON 写入，后台建出来的套餐一项可兑付权益都没有却是 `status='active'` 可售的 —— 与用户侧 M2 是同一个缺陷。更严重的是 `ensureBusinessCatalogs` 以 `status='active'` 播种月度会员，**一次后台访问就能把迁移下架的月会员重新上架**。两处已修（种子改 inactive，表单改收权益本身，只放开已实现兑付的三项）。

表格记「里程碑：`milestones` 已算出并随时间线下发，**无任何端上渲染**」。核实结果：`pages/timeline/timeline.wxml` 的里程碑区块（`.stones` / `.stone`）**已在 `b3fab7c` 提交里**，`timeline.js` 也已把 `milestones` 存进 data。E3 的真实缺口只是 2.4 表格后半句「达成当天在首页出现一次」。

1. **里程碑不做常驻标签，只在达成当天出现。** 里程碑是一个瞬间而不是一种状态；常驻会让它退化成又一个货架标签，而历史里程碑在时间线页本来就能回看。**纪念阶段一律不出现** —— 天数已按 `memorialSince` 封口，不可能「今天刚达成」，且给已离开的宠物弹一句庆祝是冒犯（与「纪念线永远克制」一致）。

2. **E5 挂时间线页尾而不是首页。** 正文 2.4 说「挂在 `commerce` 的年度报告旁或 `timeline` 页尾」，两处都做了，但**首页刻意不放**：叙事视频是四段 filtergraph 而 `processNextVideo` 队列并发是 1，放首页等于在用户还没看任何东西之前就推一个重任务。时间线页的照片正是这条片子的素材，看完一整年再看到「做成一段短片」是顺的。

### 11.5 第三批实现记录（L5/L6/L1/L2/L4 + P5）

实施顺序按 7.2：L6 体重趋势 → L5 主动提示 → L1/L2 健康交付物 → P5 恢复定价，L4 独立。

**一、需要新建三张表（正文未提）。**

L5 的「疫苗驱虫到期」需要一张记「上次什么时候、下次什么时候」的表，而**全库此前没有任何疫苗/驱虫记录**（`grep vaccine` 无结果）—— 提示无从产生。L1 的健康档案同样要这份数据。迁移 0022 建三张：

- `pet_care_records` —— 免疫/驱虫/体检记录。**只存事实不存结论**：记「打了什么、哪天打的、下次哪天」，不记「是否达标」（那是评价，接近诊断）。项目名由用户自己填、不做枚举 —— 给候选清单等于在推荐具体疫苗或驱虫药（红线 2）。
- `health_reminders` —— 提示的去重与限频。**独立于 `message_subscriptions`**：那张表是微信订阅消息通道（一次授权一次下发），而健康提示走站内通知，两者授权模型完全不同，混表会让「推过没有」和「授权没有」纠缠在一起。
- `health_documents` —— L1/L2 的产出。与 `annual_reports` 分表：那张表的唯一约束是 `(user_id, year)`，而健康档案是「按宠物 + 按导出时刻」，一年可以导多份（每次就医前都可能导一份）。**不进 `works`**，无 share_token。

另需给 `message_subscriptions` 补 `status_updated_at` 列 —— E2 的授权消耗要写它，而这张表一直没有（memberships 早有同名列）。缺了那条 UPDATE 会在运行时报错，且只在 Worker 轮次里跑，本地不起 Worker 时不暴露。

**二、L6 的边界：只做减法，不做判断。**

正文 3.3 要求「体重曲线给出『较上次 ±X%』的事实陈述，不做 BMI 与肥胖评级」。实现时把这条边界写成了两个具体决定：

- 「变化了多少」是用户自己称出来的两个数之差，我们只替他算减法；「这个体重是否健康」需要品种、年龄、体型、肌肉量与触诊 —— 而体况评分（BCS）本身就是执业兽医的触诊项目，靠体重数字算不出来。
- 提示语**不说「异常」**：异常于什么？谁定的正常范围？我们没有资格给正常范围。能说的只有「变了这么多」这个事实，加「和兽医提一下」这个动作 —— 后者把判断权交回给有资格的人，这正是分诊而非诊断的含义。
- 加了 ±1% 的「持平」区间：4kg 猫的 1% 是 40g，家用宠物秤的重复性就在这个量级，把噪声说成「上升」会让用户以为发生了什么。
- `weight-trend.test.ts` 有一条扫全部输出文本的红线守卫（15 个评价词），将来有人想加「体重偏高」会先失败。

**三、L5 的三处克制。**

- **走站内通知不走微信订阅消息**：后者要用户逐次授权（见 E2 的授权门），而健康提示的价值在于用户打开小程序时看得到 —— 站内通知不需要授权，也不会打扰。
- **单次上限 20 条**。这不是性能考虑而是体验考虑：一个养五只宠物、每只都有疫苗到期的用户一次收到十几条通知，等于没有通知。
- **senior 季度提示的措辞不带紧迫感**：「该做体检了」是提醒，「再不检查就晚了」是恐吓；也不列具体检查项目（那是兽医根据触诊决定的）。`subject_key` 用「年份+季度」而非固定日历季度起点，否则刚把宠物设成 senior 就会收到提示。

**四、L4 的 senior 调性是最难写的一档。**

正文 3.2 判断准确：`senior` 此前是空标签，「用户手动设成晚年后什么都不会变，这比没有这个选项更差 —— 它给了一个承诺然后什么都不做」。落地时定了三条边界：

- **不改名字**（还是同一个玩法，不是纪念形态）；
- **不改价格** —— 晚年阶段涨价是趁人之危，降价则暗示「这个阶段的东西不值钱」，两者都不对；
- **措辞不提「离别」「最后」「剩下的时间」** —— 那是替用户宣告一件还没发生的事，冒犯程度接近把纪念文案错用在活着的宠物上。落点是「把现在的每一天都记下来」：陈述现在，不预告将来。

纪念空间入口从「`me` 页固定展示」改为「挂在 senior/memorial 宠物的操作行」，**只改可达性不加推送**：没有弹窗、没有引导、陪伴中的宠物旁边不出现这个按钮。这补上了 C9「纪念可达性」对 senior 不成立的那一半。

**五、P5 的定价与一处真实缺陷。**

迁移 0023 发 yearly v4 ¥128，加回两项健康权益（v3 ¥69 转 inactive，已购用户按快照履约）。一次性权益合计 ¥118.8 仍低于定价，所以 `saving` 依然为 0、继续给「两件回本」—— 这条不变式与 ¥69 时期一样，只是数字变了。

**修掉的缺陷**：`breakEvenDeliverables` 原先逐项列举一次性权益做抵扣，加回两项健康权益时漏算，回本件数从 2 错成 4（测试先失败才发现）。已改为由 `singleBuyValue` 减去单件档差导出 —— 加新权益不会再漏。这类「逐项列举必然漏一项」的写法值得在别处也留意。

**六、第四批（X1/X2）。**

X1 `growth-lab-client.tsx` 核实确为零引用方（除自身与文档提及），已删。X2 `pages/growth` 已删，小程序从 24 页降为 **23 页**（CLAUDE.md 的三处页数已同步）。`me` 的入口改指首页时**必须用 `wx.switchTab`**：首页是 tabBar 页，`navigateTo` 对 tabBar 目标会直接失败且不报错到界面上，表现是点了没反应。
